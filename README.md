# 基于术中影像与 RAG 的结直肠手术围术期多模态知识库智能问答系统

本科毕业设计项目。面向结直肠手术围术期全流程，整合医学文献、诊疗指南、影像资料与典型病例，
构建专科多模态知识库，结合大语言模型与检索增强生成（RAG）技术，提供精准、可溯源的智能问答。

> **免责声明**：本系统输出仅供教学与科研参考，不构成任何诊疗建议。
> 仅使用公开文献与公开脱敏影像，不接入真实患者数据。

### 4b.4 自动标注与准确率

分期（preop/intraop/postop/general）与证据等级均自动标注：

- **分期**：规则 + 关键词加权。三类得分接近时判为 `general`（跨期通用），

- **证据等级**：优先用 PubMed `PublicationType`（最权威），
  其次用中文关键词（指南/共识），最后按标题特征兜底。

**实测准确率**（对比种子清单预期值）：

| 标注类型 | 准确率 | 说明 |
|----------|--------|------|
| 分期 | 约 71% | 边界案例（如 ERAS 文献同时涉及前中后三期）易判为 general |
| 证据等级 | 约 50%（手工录入） | **手工录入的摘要无 `PublicationType`，判定依据最弱** |
| 证据等级 | **约 86%**（PubMed 来源） | 有 `PublicationType` 时准确率显著提升 |

> **结论**：证据等级判定的关键是 PubMed 的结构化出版类型。

## 四之三、多路召回与 RRF 融合（阶段三）

### 4c.1 架构

```
查询
 ├─ 向量召回（BGE-M3 + pgvector HNSW）      权重 1.0   —— 语义相近、跨语言
 ├─ 关键词召回（中文 bigram + GIN 倒排）     权重 0.7   —— 字面精确
 └─ 图谱路径召回（Neo4j）                    权重 0.6
        ↓
    RRF 倒数排名融合（只用名次，不用分数）
        ↓
    交叉编码器重排（可选）
        ↓
    证据等级加权 + 同文献限流
        ↓
    最终结果（带引用溯源元数据）
```

### 4c.2 为什么用 RRF 而不是加权分数求和

各路的分数**不可直接比较**：向量相似度是余弦值（集中在 0.4~0.9），
关键词得分是命中比例（分布形态完全不同）。直接加权求和需要反复调参，
换数据集即失效。RRF 只用**名次**：

```
RRF(d) = Σ_i  weight_i / (k + rank_i(d))        k = 60
```

对分数尺度不敏感，无需归一化，在多个召回列表中同时靠前的文档获得最高分，
天然实现「共识投票」。参考 Cormack et al., SIGIR 2009。

### 4c.3 关键词召回必须做重叠度过滤（重要设计决策）

**问题**：初版实现中，多路融合的准确率**低于**纯向量检索
（标题反查 R@1 由 1.000 跌至 0.250）。

**根因**：bigram 重叠匹配过于宽松。查询越长产生的 bigram 越多，
而任意两段中文医学文本都会共享若干高频词元（"术后""治疗""患者"）。
这些仅共享 1~2 个常见词元的无关文档被关键词路召回并排在前列，
**RRF 只用名次不用分数**，于是它们被当成「多路共识」而提权，反而毒化了结果。

**解法**：按最小重叠比例过滤（`min_keyword_overlap`，默认 0.3）。

> 这不是可选的性能优化，而是本方案能成立的必要条件。
> 论文中应报告该阈值的影响（截止目前：0.0 → 融合劣于纯向量；0.3 → 融合不劣于纯向量）。

| ① 仅向量 | 0.700 | 0.850 | 0.766 | 155ms |
| ② 仅关键词 | 0.325 | 0.325 | 0.325 | 98ms |
| ③ 多路融合(RRF) | 0.600 | 0.850 | 0.699 | 246ms |
| **④ +重排** | **0.900** | **0.925** | **0.915** | 1203ms |
| ⑤ +重排+证据加权 | 0.825 | 0.925 | 0.871 | 1264ms |
| ⑥ 融合-不过滤关键词 | 0.775 | 0.875 | 0.820 | **13340ms** |

标题反查：

| 配置 | R@1 | R@5 | MRR | 延迟 |
|------|-----|-----|-----|------|
| **① 仅向量** | **1.000** | **1.000** | **1.000** | 1564ms |
| ② 仅关键词 | 0.625 | 0.625 | 0.625 | 93ms |
| ③ 多路融合(RRF) | 0.650 | 0.800 | 0.720 | 244ms |
| ④ +重排 | 0.975 | 1.000 | 0.988 | 1657ms |
| ⑤ +重排+证据加权 | 0.700 | 0.950 | 0.797 | 1503ms |
| ⑥ 融合-不过滤关键词 | 0.700 | 0.950 | 0.797 | **6243ms** |

### 4c.5 四个必须如实写进论文的发现

**发现 1：重排是收益最大的单一组件。**
摘要片段反查中 MRR 由 0.766（仅向量）提升至 **0.915**，**+14.9 个百分点**。
交叉编码器逐对精算，是小规模候选集上性价比最高的手段。

**发现 2：关键词重叠度过滤的主要价值是延迟，不是准确率。**
这是实测修正了初始假设的结论。第 ⑥ 组（不过滤）与第 ⑤ 组准确率基本相同
（摘要 MRR 0.820 vs 0.871；标题完全相同），但**延迟高 4~10 倍**
（摘要 13340ms vs 1264ms）。原因：不过滤时关键词路把几乎所有共享
常见词元的文档都召回，候选池膨胀数倍，重排开销随之线性上升。

> 论文表述建议：「重叠度过滤在准确率上中性，但将端到端检索延迟降低
> 4~10 倍，是保证系统可用性的必要工程措施。」

**发现 3（关键，不要回避）：在「标题反查」上多路融合不如纯向量。**
仅向量 R@1=1.000，融合+重排 0.975。原因已定位：

> 标题反查是**精确文本匹配**任务——标题块本身就在库中，
> 余弦相似度接近 1，向量检索直接命中。
> 而关键词路会因共享常见医学术语（"术后""治疗"）引入竞争者，
> RRF 只看名次不看分数，这些噪声被当作「多路共识」提权。

**这个任务对融合最不利**，不能据此否定融合的价值：
- 真实用户提问（"吻合口漏怎么处理"）不会与库中文本逐字相同，
  此时关键词的精确匹配是**互补**而非竞争
- 摘要片段反查（非逐字）已显示融合不劣于纯向量（R@5 均为 0.850）

**论文应同时报告这两组结果，并说明评测任务特性对结论的影响。**
阶段十将用人工标注的真实临床问题评测集给出最终结论。

**发现 4：证据等级加权的效果依赖任务特性。**
修正公式后（见 4c.6），摘要片段反查上加权使 MRR 由 0.915 微降至 0.871，
但在「指南优先」这一领域目标上是有意为之的取舍——
论文应报告「top-3 中高证据等级内容占比」这一辅助指标，
而非仅看 Recall/MRR，才能体现该策略的真实价值。

### 4c.6 单元测试

核心融合逻辑有独立单测（不依赖数据库与 GPU）：

```powershell
& $py -m pytest backend\tests\test_fusion.py -v
```

**25 项全部通过**，覆盖：
- RRF 公式正确性、跨路去重、权重影响、k 平滑效果、共识排序
- 证据等级加权（相近分数时指南反超、低相关高等级文档不跨越、加分有界）
- 同文献限流、关键词重叠打分边界

测试过程中发现并修复了两个真实缺陷：

1. **RRF 就地改写输入对象的 `rrf_score`**，导致同一批对象被多次融合时
   后一次覆盖前一次，结果不可复现。改为 `dataclasses.replace` 生成副本。
2. **证据加权公式错误**。初版用线性插值 `base*(1-s)+base*norm*s`，
   会把「低相关但高证据等级」的文档抬到「高相关」文档之上
   （强度 0.8 时指南分 0.1→0.42，综述分 0.95→0.36，排序完全颠倒）。
   改为**乘法加权** `base*(1+strength*norm)`，加分幅度正比于原分，
   实测使证据加权在标题反查上由 0.754 恢复到 0.797。

## 四之四、答案生成与引用溯源（阶段四）

### 4d.1 闭环流程

```
用户提问
   ↓
① 检索（多路召回 + RRF 融合 + 重排）      ← 阶段三
   ↓
② 证据组装（编号 + 元数据，供 LLM 引用）
   ↓
③ LLM 生成（约束：仅依据证据、内联标注 [n]）
   ↓
④ 引用解析（[n] → 真实文献、页码、证据等级）
   ↓
带引用溯源的答案
```

### 4d.2 为什么用「内联标记」而非结构化 JSON

结构化 JSON 输出（含 citations 数组）便于解析，但**无法流式显示**——
用户必须等完整 JSON 生成完才能看到答案。

本系统要求 LLM 在答案正文中内联标注 `[1][2]`，后端用正则解析并映射回
真实 chunk。这样：答案可逐字流式输出（体验好），引用关系事后解析（可溯源）。

支持的标记写法：`[1]`、`[1][3]`、`[1,2]`、`[1，2]`（全角）、`[1-3]`。

### 4d.3 防幻觉的三道防线

医学场景对幻觉零容忍，系统设计了三道防线：

**防线 1（检索层）**：检索结果为空 → 不调用 LLM，直接返回提示。

**防线 2（阈值层）**：最高相关度低于 `min_evidence_score`（默认 0.05）
→ 不调用 LLM，返回「相关性不足」提示。

**防线 3（生成层）**：提示词硬约束——

```
1. 只依据提供的「证据片段」作答。不要使用你自己的医学知识补充或推测。
   如果证据片段中没有相关信息，必须明确回答"提供的资料中未包含相关信息"。
2. 每个结论都要标注来源编号。
3. 禁止编造。不要虚构文献、数据、剂量或结论。
```

**防线 4（校验层）**：解析引用时校验编号是否真实存在，
LLM 引用了不存在的编号则记入 `invalid_citations` 并剔除（幻觉信号可监控）。

**实测效果**：对知识库未覆盖的问题（"如何用针灸治疗结直肠癌术后肠梗阻的五行辨证选穴？"），
系统正确回答"提供的资料中未包含相关信息"，并逐条说明「证据1是诊疗规范但未涉及针灸内容」，
`invalid_citations` 为空。

### 4d.4 实测问答质量示例

问："结直肠癌术后吻合口漏应该如何处理？"

系统生成的答案结构完整（总体原则 → 按临床情形分层 → 诊断识别 → 预防 → 特殊类型 → 卫生经济学），
每个结论都标注来源，并**主动提示证据局限**：

> **资料不足之处**：提供的证据片段中**未包含**具体的手术操作步骤细节、
> 抗生素种类与剂量方案、引流管拔除时机…

另一例中系统主动指出：

> 需注意，证据[3]针对的是根治性膀胱切除术患者，并非结直肠手术人群，引用时需谨慎。

**这类「主动声明证据边界」的行为是提示词约束的直接效果**，也是医学 RAG 系统
区别于通用问答的关键，论文中应作为案例展示。

### 4d.5 性能实测

| 指标 | 实测值 |
|------|--------|
| 检索耗时（模型已驻留） | 1.4 ~ 1.6 秒 |
| **生成耗时（中位，n=4）** | **4.59 秒**（min 3.42 / max 7.19） |
| 流式首字延迟 | 约 4.0 秒 |
| 单次 token 用量 | prompt 364~1476 / completion 401~731 |
| 引用准确率 | 实测无编造引用（`invalid_citations` 均为空） |

> **关于延迟的说明（重要）**：阶段四首次验证测得生成耗时 15~32 秒，
> 但经多次采样修正，实际中位耗时为 **4.59 秒**。首次测量的偏差来自
> 更长的提示词（5 条证据 vs 3 条）、模型侧冷启动与 API 波动。
> 完整分析见 `docs/模型选型与延迟优化决策.md`。

> **模型选择说明（重要）**：DeepSeek 当前可用模型为
> `deepseek-flash` 与 `deepseek-v4-pro`（`GET /models` 可查）。
> **写 `deepseek-chat` 等旧名会静默回退到 `deepseek-flash`**。
> 而 `deepseek-flash` 是推理模型，推理内容计入 `max_tokens`，
> 额度偏小会在推理阶段耗尽、导致 `content` 为空——实测
> `max_tokens=512` 时 100% 返回**空答案**，`=1024` 时 4 次中出现 1 次。
>
> 因此：默认模型用 `deepseek-v4-pro`，`LLM_MAX_TOKENS` 提到 4096，
> 并在客户端对空答案**显式抛错**（而非静默返回空字符串）。

> **两段式方案已评估并否决**：曾考虑「flash 出草稿 + v4-pro 精修」以改善
> 首字延迟，但实测两模型延迟相当（flash@4096 中位 5.12s vs v4-pro@4096
> 中位 4.59s），两段式串行总耗时 **9.71 秒，反而比单段慢 5.1 秒**。
> 根因：延迟来自推理机制本身（推理占生成 token 的 68~85%），
> 换模型或叠加模型都无法规避。详见 `docs/模型选型与延迟优化决策.md`。

### 4e.1.1 一键启动（推荐）

共有两种方式：

**方式一：双击 `start.bat`**（最省事）

这是纯 ASCII 的批处理包装，内部调用 `start-all.ps1`，自动完成：
检查前置条件 → 启动 Docker → 启动后端（**自动停掉旧版本进程**）
→ **预热检索模型** → 启动前端 → 输出访问地址。

**方式二：PowerShell 命令行**

```powershell
cd D:\AI\RAG_project
.\start-all.ps1
```

或跳过模型预热：`.\start-all.ps1 -SkipWarmup`

> **为什么需要 `start.bat` 包装，不能直接双击 `.ps1`？**
>
> 1. `.ps1` 双击会被 Windows 用记事本打开，**不会执行**
> 2. 默认执行策略为 `RemoteSigned`，会拦截未签名的本地脚本
> 3. 批处理调用 PowerShell 时加 `-ExecutionPolicy Bypass`，
>    该参数**仅对本次运行生效**，不修改系统设置
>
> **踩坑记录 1：批处理文件绝不能含非 ASCII 字符**
>
> 最初把中文提示写在 `.bat` 里，结果完全无法运行 —— 报
> `'se' is not recognized as an internal or external command`，
> 连 `echo` 关键字都被拆碎。换成 GBK 编码后仍失败。
>
> 根因：批处理的正确解析要求**三者代码页完全一致** ——
> 文件编码、cmd 解析代码页、控制台输出代码页。
> 而 `chcp` 只在执行到该行时才改变控制台代码页，
> 文件却早已按启动时的代码页解析完毕，中文随即被拆成非法命令。
>
> 解决：`start.bat` 保持**纯 ASCII**，中文界面全部由
> `start-all.ps1` 输出（UTF-8 带 BOM，可被 PowerShell 稳定解码），
> 批处理内用 `chcp 65001` 保证其输出正确渲染。
> **这是 Windows 批处理的通用原则：批处理里不要写非 ASCII 文本。**
>
> **踩坑记录 2：`$ErrorActionPreference = "Stop"` 与 docker 不兼容**
>
> 首版脚本在第 2 步就中止，报
> `Container cr-postgres Running : RemoteException`。
>
> 根因：`docker compose up -d` 在容器已运行时，会把
> `Container xxx Running` 这类**正常状态信息写入 stderr**。
> 而 `Stop` 模式下，stderr 输出经 `2>&1` 合并后会被
> 当成致命错误抛出 —— 实际上命令成功退出（码 0）。
>
> 解决：脚本改用 `$ErrorActionPreference = "Continue"`，
> 统一按 `$LASTEXITCODE` 判断原生命令成败，关键步骤单独 try/catch。
>
> **踩坑记录 3：FastAPI 默认 JSON 响应导致 PowerShell 中文乱码**
>
> 预热步骤显示 `?¨?????·2???è????? 91.3 ?§?`。
>
> 根因：FastAPI 的 `JSONResponse` 返回 `application/json`（**不带 charset**），
> 而 Windows PowerShell 5.1 的 `Invoke-RestMethod` 在缺少 charset 时
> 按 ISO-8859-1 解码，中文随即损坏。
>
> 解决：在 `app/main.py` 定义 `UTF8JSONResponse`（`media_type` 含
> `charset=utf-8`）并设为 `default_response_class`。
> 浏览器与 httpx 本就能正确解码，此改动只是让 PowerShell、curl
> 等客户端也能正确显示，无副作用。

### 4e.1.2 模型预热的实际耗时

### 4e.3 三个关键交互设计

**设计 1：思考指示器（解决 4~10 秒等待的体验问题）**

LLM 为推理模型，先思考再输出，首字延迟 3~5 秒。若期间界面空白，
用户会以为系统卡死。因此问答页实现分阶段反馈：

```
retrieving  → 「正在检索知识库证据…」 + 骨架屏动画
generating  → 「正在推理并组织答案…」 + 已等待秒数（实时递增）
```

**等待秒数实时显示**是关键——让用户确认系统在推进，而非无响应。

**设计 2：引用双向联动**

- 点击答案中的 `[n]` 上标 → 右侧面板高亮对应文献并滚动到该条目
- 点击右侧文献条目 → 答案中对应标记高亮

引用标记的后端实现：LLM 在答案正文内联标注 `[n]`，
后端正则解析并映射回真实 chunk（见 4d.2）。

**设计 3：证据等级双重标识**

证据等级同时用**颜色**与**中文名**标识：
- 颜色便于快速扫视（指南=红、系统评价=紫、RCT=蓝、综述=绿、病例=灰）
- 中文名避免色盲用户无法区分（医学系统对可访问性要求更高）

### 4e.4 前端开发中解决的三个技术问题

**问题 1：SSE 无法逐字显示（Vite 代理缓冲）**

现象：流式接口返回正常，但前端一次性收到全部内容。

根因：Vite 的 `http-proxy` 默认会缓冲响应体，破坏了 SSE 的流式语义。

解决：在 `vite.config.ts` 中对 `text/event-stream` 响应显式关闭缓冲：

```ts
proxy.on('proxyRes', (proxyRes) => {
  if (proxyRes.headers['content-type']?.includes('text/event-stream')) {
    proxyRes.headers['x-accel-buffering'] = 'no'
    proxyRes.headers['cache-control'] = 'no-cache'
  }
})
```

**实测验证**：单次问答收到 **230~713 个增量块**，确认逐字输出正常。

**问题 2：SSE 解析被 TCP 分片破坏**

SSE 是字节流，一条事件可能被拆到多个 chunk，一个 chunk 也可能含多条事件。
若对每个 chunk 直接 `JSON.parse` 会随机失败。

解决：用缓冲区累积文本，按 `\n\n` 切出**完整事件**后再解析，
并处理流结束时残留的最后一条事件（详见 `src/api/client.ts`）。

**问题 3：LLM 输出渲染的 XSS 风险**

答案由 LLM 生成，属不可信内容。虽经 markdown-it，但若放行原始 HTML
则可能注入脚本。

解决（双重防护）：
- markdown-it 设 `html: false`（不解析原始 HTML）
- 再用 DOMPurify 白名单过滤标签与属性

**问题 4：引用标记还原失败（哨兵标记法）**

现象：答案只显示一行即中断，且 `<sup class="cite">` **以字面文本出现在页面上**，
引用面板显示「未引用任何文献」但底栏却显示「引用 4 条」。

根因：初版把引用标签包在反引号中交给 markdown-it，事后再从 `<code>` 还原：

```
markdown-it 输出：<code>&lt;sup class=&quot;cite&quot;...&gt;</code>
```

还原正则需同时匹配 `&lt;` `&quot;` `&gt;` 三种转义形式，极其脆弱，
实测**完全无法还原**，引用标记与 `**` 粗体标记一并以字面文本显示。

解决：改为**哨兵标记法**，分三步：

```
① [1] → @@CITE1@@                    （哨兵只含字母数字与 @）
② 交给 markdown-it 渲染               （哨兵是普通文本，不被转义或改写）
③ 在结果 HTML 中把哨兵替换为 <sup class="cite">
```

哨兵不含 `<` `>` `&` `"`，能安全穿过 markdown-it 的转义流程，
还原时也不存在歧义。

**验证结果（Node + jsdom 跑真实 `markdown.ts`）**：10/10 检查通过 ——
标题渲染为 `h2/h3`、粗体渲染为 `strong`、列表与表格正确、
11 个引用上标全部生成、无残留哨兵、无字面 `**`、无字面 `&lt;sup`。

**问题 5：并发提问产生「有提问无回答」的孤儿消息**

现象：界面出现两条相同提问，但只有一条回答，引用面板为空。

根因：`ask()` 的并发保护写作 `if (!text || isBusy.value) return`，
判定虽在状态修改之前（正确），但 `QaView.send()` 之外的调用入口
（示例问题、重新生成）会**静默丢弃**提问。

解决：把并发判定与状态修改显式分离并加注释，
`QaView.send()` 改为明确提示「正在生成回答，请等待完成或点击停止生成后再提问」，
且**保留输入框内容**避免用户输入丢失。

**问题 6：Vite 文件监听器被临时目录击溃（EBUSY 崩溃）**

现象：dev server 直接退出，报
`EBUSY: resource busy or locked, watch '...\.chat.ts.*.tmpdir\chat.ts.tmp'`。

根因：代码编辑工具写入文件时会创建 `.xxx.tmpdir/` 临时目录，
Vite 的 `FSWatcher` 尝试监听它，遇到文件锁后抛出未捕获异常导致进程退出。

解决：在 `vite.config.ts` 中配置 `server.watch.ignored` 显式忽略
`**/*.tmpdir/**`，并在 `.gitignore` 中加入 `*.tmpdir/`。
**这是根治**——只清理残留目录只能治标，编辑代码时仍会复发。

**问题 7：Vite 开发代理丢失 SSE 事件，导致答案残缺**

现象：答案只显示前几行，但底栏显示「引用 N 条」与耗时（说明状态已完成），
浏览器控制台**无任何报错**。

定位过程（关键数据对比）：

| 路径 | delta 事件数 | 答案长度 |
|------|-------------|---------|
| 直连后端 8000 | **607** | **1053 字符** |
| 经 Vite 代理 5173 | **573** | **952 字符** |

**结论：Vite 开发服务器的 SSE 代理丢失约 34 个事件（约 10% 内容），且不报错。**

进一步验证：
- 直连 LLM 流式接口：589 个片段、0 个 JSON 解析失败、拼接完整 → **LLM 侧无损**
- 非流式接口经代理：1008 字符、以句号完整结束 → **非流式经过代理可靠**

**解决方案：流式体验 + 自动补偿**

```
① 优先用流式（逐字显示，体验好）
② onDone 时做完整性校验：
     · 长度一致性：本地累积 delta vs 服务端答案
     · 句末完整性：答案是否以句末标点结尾（截断的典型特征）
③ 任一不满足 → 自动调用**非流式接口**重新获取权威答案并替换
```

**为什么必须做句末校验**：截断的答案通常停在句子中间（无句末标点），
这比长度比对更鲁棒 —— 长度差异可能源于模型重排，而句末缺失几乎总意味着不完整。

**为什么必须自动补偿**：医学场景下丢一个「征」字即改变语义
（`引流的具体指、方式` vs `引流的具体指**征**、方式`）。
系统绝不能安静地展示残缺的医学答案 —— 正确性优先于流式体验与 token 成本。

**生产部署建议**：Vite 代理仅存在于开发模式。答辩演示建议使用
`npm run build` + `npm run preview`（静态服务，不经该代理），
可从根源避免此问题。

**问题 8（最关键）：Vue 响应性失效 —— 修改原始对象而非响应式代理**

现象：诊断条显示 `原始 1111 字 · 渲染 22 字 · 引用数组 4 · 状态 done`。
**数据层完全正确**（1111 字符完整答案），但界面只显示首个流式片段，
浏览器控制台**无任何报错**。

定位：`22` 这个数字是破案关键 —— 它恰好等于
`<p><strong>加速康复外科（ERAS）</strong></p>` 的长度，
即**只有第一个 delta 片段被渲染**。说明 `message.content` 变了，
但 `renderedHtml` 再也没重新计算。

用最小实验验证（Vue 3 `ref` 数组 + `computed`）：

| 场景 | 数组内对象 content | 修改后 computed 观测值 |
|------|-------------------|----------------------|
| A：闭包持有 **push 前的原始对象** | 101 字符 | **0 字符（不更新）** |
| B：**从数组取回**对象再修改 | 101 字符 | **101 字符（正常）** |

判决性证据：`messages.value[0] === assistant` 返回 **`false`**。

根因：Vue 3 的 `ref([])` 在 `push` 时会把对象包装为**响应式代理**存入数组，
而局部变量仍指向**原始对象**。修改原始对象不经过代理，
不会触发任何依赖该对象的 `computed` 与模板重新求值。

错误写法：

```ts
const assistant: ChatMessage = { id, role: 'assistant', content: '', ... }
messages.value.push(assistant)
// ❌ assistant 是原始对象，后续 assistant.content += text 不触发更新
```

正确写法：

```ts
messages.value.push({ id, role: 'assistant', content: '', ... })
const assistant = messages.value[messages.value.length - 1]
// ✓ 从数组取回的是响应式代理，后续修改正常触发更新
```

**这个坑的迷惑性极强**：
- 数据层正确（`content` 确实是完整答案，诊断条也证明了）
- 控制台无报错
- 渲染函数本身正确（单测通过）
- 只有「界面停在第一次渲染结果」这一个症状

**修复范围**：`ask()` 的助手消息创建、`repairAnswer()` 的补偿写入，
均改为从响应式数组按 id / 索引取回对象后再操作。

**验证**：模拟完整流式过程，响应式触发 **77 次**、
渲染长度随内容增长、粗体/引用/列表全部正确渲染。

> **经验总结**：Vue 3 中「把对象 push 进 reactive 数组后再修改原变量」
> 是高频陷阱。凡是需要在 push 后继续操作该对象，**必须从数组取回**。

### 4e.5 模型切换：改用 deepseek-flash（重要修正）

阶段四曾选用 `deepseek-v4-pro`，理由是「flash 会返回空答案」。
但用**真实 RAG 提示词**（3108 字符 / 5 条证据）重测后结论改变：

| 模型 | 首字延迟 | 总耗时 | 答案字符数 |
|------|---------|--------|-----------|
| **deepseek-flash** | **2.02s / 3.16s** | **5.48s / 6.72s** | 689 / 727 |
| deepseek-v4-pro | 13.61s / 8.85s | 15.45s / 9.98s | 236 / 138 |

**flash 在速度与质量上均优于 v4-pro**：不仅快 2~3 倍，答案结构也更完整
（六章节 + 明确列出「资料未涵盖的内容」，并指出「证据3、证据4仅提供题名信息」）。

**此前误判的原因**：基准测试用了仅 364 token 的短提示词，
推理开销占比小，掩盖了两个模型的真实差异。
**这提醒我们：性能基准必须使用真实长度的输入。**

> 空答案问题并非 flash 独有，而是**推理模型 + max_tokens 不足**的共性行为
> （实测 `max_tokens=512` 时 100% 空答案）。现已在客户端实现：
> 捕获 `reasoning_content` + 空答案**显式报错** + **偶发空答案自动重试**。

| 指标 | 实测 |
|------|------|

> **踩坑记录：测量方法本身会污染延迟数据**
>
> 最初用 `read(1)` 逐字节读取 SSE 流，测得首字延迟 **13.99 秒**；
> 改为 `read(4096)` 分块读取后降至 **3.64 秒**。
>

>
> **教训**：性能测量必须模拟真实客户端的读取方式，
> 否则会把测量开销误判为系统延迟。

## 四之六、评测与实验（阶段十）

> 历史实验记录：本节 195/189 题的金标准 ID 已不能匹配当前语料，旧指标不能用于当前版本效果证明。当前固定 12 题开发集与五组配置见 [检索评测与复核报告](docs/检索评测与复核报告.md)；尚未独立临床复核。

### 4f.1 评测集构建

**为什么需要自建评测集**：前期的自动评测（用文献标题反查自身）只反映
「已知条目查找」能力，无法回答论文最关心的问题——**系统对真实临床提问的效果如何？**

**构建方式**：从知识库文本块反向生成问题（LLM 出题 + gold chunk 客观标注）

```
挑选内容充实的文本块（>300 字符，每篇文献最多 2 块）
   ↓ LLM 依据块内容生成临床问题
   ↓ 提示词强制要求：口语化提问 + 禁止照抄原文短语（避免词汇泄漏）
   ↓ 该文本块即 gold chunk（检索评测的客观依据）
```

**关键约束：防止词汇泄漏**。若让 LLM 直接「根据这段文字提问」，它会逐字摘抄
原文术语，导致关键词检索虚高、评测失去意义。因此提示词要求换用同义表达。

实测生成的问题质量示例：

> 「用人工智能判断结直肠癌术前淋巴结有没有转移，目前这方面的证据是怎么汇总出来的？」
> 「肥胖的直肠癌病人做微创手术，用机器人跟用普通腹腔镜比，围手术期的结果有差别吗？」

**两套评测集（用于对照实验）**：

| 评测集 | 题目数 | 语言 | 用途 |
|--------|--------|------|------|
| 中文口语提问 | **195** | 中文 | 揭示跨语言检索约束 |
| 英文口语提问 | **189** | 英文 | 同语言对照，公平评估关键词路 |

语料规模：444 篇文献 / 1661 个文本块（**99% 为英文文献**）。

分布（中文集）：术后 29% / 术前 26% / 通用 24% / 术中 21%；
处理治疗 42% / 比较选择 19% / 证据预后等其余类型。

### 4f.2 检索消融实验（核心结果）

| 配置 | 中文 R@1 | 中文 R@5 | 中文 MRR | 英文 R@1 | 英文 R@5 | 英文 MRR |
|------|---------|---------|---------|---------|---------|---------|
| ① 仅向量 | 0.072 | 0.344 | 0.184 | 0.164 | 0.487 | 0.296 |
| ② 仅关键词 | **0.000** | **0.000** | 0.000 | **0.005** | **0.005** | 0.005 |
| ③ 多路融合 | 0.072 | 0.344 | 0.184 | 0.122 | 0.466 | 0.252 |
| ④ **+交叉编码器重排** | **0.297** | **0.579** | **0.407** | **0.370** | **0.651** | **0.485** |
| ⑤ +重排+证据加权 | 0.256 | 0.564 | 0.384 | 0.312 | 0.603 | 0.435 |

### 4f.3 四个必须如实写进论文的发现

**发现 1：重排是唯一显著有效的组件（+16~24 个百分点）**

英文集 R@5 由 0.487（仅向量）提升至 **0.651**，MRR 由 0.296 提升至 **0.485**
（**+19.0 个百分点**）。中文集 R@5 提升 **+23.6 个百分点**。

交叉编码器逐对精算，是收益最大的一环。这是本系统最确定的结论。

**发现 2（颠覆性）：关键词检索对自然语言提问几乎完全失效**

| 数据集 | 关键词路 R@5 | 说明 |
|--------|-------------|------|
| 中文提问 | **0.000** | 词元完全无法重叠 |
| 英文提问 | **0.005** | **同语言下仍然失效** |

**英文对照实验是关键**：它排除了「跨语言」这一解释。
真正原因是**口语提问与学术文本的词汇体系根本不同**：

```
医师问：这两个术式在并发症上有什么区别？
文献写：robotic versus conventional laparoscopic surgery
```

bigram 是精确词元匹配，无法跨越这种表述差异。
**这否定了「关键词检索可补充语义检索」这一常见假设**（至少在本任务上）。

**发现 3：RRF 融合在关键词路失效时反而降低效果**

英文集：仅向量 R@5 = 0.487，多路融合（关键词权重 0.7）= **0.466（下降 2.1 个百分点）**。

原因：RRF 只使用**名次**不使用分数。关键词路虽然几乎不含正确答案，
但它返回的结果在自身列表中排名靠前，被 RRF 当成「多路共识」而提权，
从而把向量路的正确结果挤下去。**这是 RRF 在弱召回源上的固有缺陷。**

**改进措施**：将关键词权重由 0.7 降至 0.3（见 4f.4 的验证）。

**发现 4：证据等级加权对召回指标为负向**

英文集：+重排 R@5 = 0.651 → +证据加权 = 0.603（**-4.8 个百分点**）。
中文集：0.579 → 0.564（-1.5 个百分点）。

原因：该策略按证据等级提升分数，会把「高证据等级但与问题相关性稍低」的文档
排到前面，从而挤掉真正相关的文档。

> **需要说明的取舍**：召回指标下降不等于该策略错误。
> 医学场景中「指南优先于病例报告」是合理需求，
> 但它的价值应通过**「top-3 中高证据等级内容占比」**这类指标衡量，
> 而非 Recall/MRR。论文中应同时报告两类指标，而非只用召回指标否定该策略。

### 4f.4 基于评测结果的系统改进

**改进 1：关键词路权重由 0.7 降至 0.3**

依据发现 3，降低弱召回源的权重可减少其对 RRF 的污染。

**改进 2：LLM 生成长度上限由 4096 提升至 8192**

实测推理模型（deepseek-flash）在复杂医学问题上的思考过程可达
**14000+ 字符**，4096 额度会在推理阶段即耗尽，导致返回空内容
（`finish_reason='length'`）。这是推理模型特有的失败模式，
已在客户端显式识别并重试。

### 4f.5 生成质量评测（LLM 裁判）

**为什么用 LLM 裁判**：忠实度、相关性这类指标无法用字符串匹配计算，
需要语义判断。评测维度与评分标准见 `app/eval/runner.py` 的
`JUDGE_SYSTEM_PROMPT`。

**关键评分原则**：答案明确说明「资料未包含」是**正确行为**，
不应因信息少而扣分 —— 否则会鼓励模型编造。

**最终结果（40 题抽样，40/40 全部评判成功）**：

| 指标 | 数值 | 含义 |
|------|------|------|
| 相关性 | **1.000** | 全部切题 |
| 引用准确率 | **0.807** | 约 1/5 引用不够精确 |
| 忠实度 | **0.766** | 约 23% 论断证据支撑不足 |
| **幻觉引用率** | **0.000** | 40 条答案**无一编造引用编号** |
| **数值错误率** | **4.6%** | 175 处数值中 8 处无据（结构化检查） |
| 含无据数值的答案 | 4 / 40 条 | — |
| 平均答案长度 | 1287 字符 | — |
| 平均引用数 | 4.55 条 | — |
| 平均生成延迟 | 10.7 秒 | 含检索与 LLM 生成 |

> **样本量的教训**：n=20 时忠实度为 0.865，n=40 时降至 0.733~0.766。
> 样本量翻倍后指标明显下降 —— 小样本会系统性高估系统质量。
> 论文中必须报告样本量，且不宜用 20 条样本下结论。

### 4f.6 提示词加固实验：一个诚实的负面结果

**背景**：裁判评语显示最危险的幻觉不是整段编造，
而是**编造看起来专业的精确细节**（如「中转率 7.1% vs 3.4%」）。
临床医师看到具体百分比会本能信任，这类错误危害最大。

**实验设计**：在系统提示词中新增三条硬约束后，用**同一批 40 题**复测：

1. 任何数字、百分比、比值、样本量、P 值必须能在证据片段中逐字找到
2. 不得把 A 文献的结论归因给 B 文献
3. 不得外推片段未提及的人群与结局

**结果（三次运行的对比）**：

| 指标 | ① 基线提示词 | ② 加固后 | ③ 加固+证据修复 |
|------|-------------|---------|----------------|
| 忠实度 | 0.733 | 0.721 | **0.766** |
| 引用准确率 | 0.754 | 0.762 | **0.807** |
| 评语提及编造 | 85% | **95%（变差）** | — |
| 数值编造占比 | 22% | **26%（变差）** | — |
| 归因错误 | 1 条 | **0 条（修正）** | — |

**结论：提示词加固对数值编造基本无效。**
个别编造案例（PROSPECT/NORAD 试验名、30% pCR）在后两次运行中**逐字重现**，
说明模型生成临床数字的先验过强，**无法通过提示词消除**。
唯一有效的是归因规则（2 条 → 0 条）。

> 这个负面结果本身有论文价值：**它证明「提示词工程」不足以解决医学 RAG
> 的忠实度问题，必须引入结构化的运行期校验。**

### 4f.7 结构性防线：数值主张核验（针对上述失败模式）

既然提示词无法解决，本系统增加**独立于提示词的校验层**：

```
答案生成完成
   ↓ 正则提取数值主张（百分比 / 比值 / 样本量 / 时长）
   ↓ 与检索到的完整证据正文比对
   ↓ 找不到的数字 → 写入 unsupported_numbers 字段
                  → 生成 numeric_warning 提示语返回前端
```

**实现要点**（`app/services/citation.py`）：

- **召回导向**：宁可漏报也不误报。把有据的数字误标为「无据」
  会损害用户信任，因此需归一化后匹配（去千分位、百分比与小数互转）
- **必须用完整证据正文核验**：实测若用截断文本（评测时为控制 token
  截到 900 字符）比对，证据中真实存在的数字会落在截断之外，
  **误报率可达 100%**。这是实现中踩过的真实坑
- 排除年份（如「2024 年」）以免误报

**实测捕获的编造**（LLM 裁判未明确指出的）：

| 样本 | 无据数值 |
|------|---------|
| q0025 机器人 vs 腹腔镜远期肿瘤学 | `42 例` |
| q0034 ERAS 依从性与总生存 | `30 天` |
| q0037 机器人 vs 腹腔镜优势 | `42 例`（出现 2 次） |
| q0038 低位直肠癌排便功能 | `97.0%`、`75.9%`、`32.8%`、`35.3%` |

**数值错误率仅 4.6%（8/175）**，说明本系统的数值可靠性实际较好 ——
但正是这 4.6% 最危险，必须有机制显式标注。

### 4f2.2 构建过程中解决的问题

**问题 1：APOC 扩展不可用**

本环境 Neo4j 5.26.31 社区版**未安装 APOC**，`apoc.coll.toSet` 报
`Unknown function`。改用纯 Cypher 的 `reduce` 实现列表去重：

```cypher
e.chunk_ids = reduce(
    acc = coalesce(e.chunk_ids, []), x IN coalesce(row.chunk_ids, []) |
    CASE WHEN x IN acc THEN acc ELSE acc + x END
)
```

验证：`['c1','c2']` 合并 `['c2','c3']` → `['c1','c2','c3']`（幂等正确）。

**问题 2：实体分类错误（procedure vs treatment）**

首轮抽取把「放化疗」「化疗」「免疫治疗」归入 `procedure`（手术操作），
但它们并非外科手术。新增 `treatment`（非手术治疗）类型并在提示词中
明确区分，使本体更严谨。

**问题 3：关系写入必须先于实体**

`upsert_relations` 用 `MATCH` 定位两端节点 —— 若节点尚未创建，
MATCH 无结果，关系会被**静默丢弃**。实测尝试写入 1831 条关系，
实际落库 1380 条，差额 451 条即由此产生（这是预期行为，
因为我在抽取层已校验两端必须同块出现）。写入顺序必须为：**实体先，关系后**。

**问题 4：实体索引的 70 秒冷启动**

图谱检索需为 1423 个实体名编码向量（约 61~78 秒），每次重启后端都要等待。
加入**磁盘缓存**（以「节点数 + 前 50 个实体名」的哈希为指纹，
图谱重建后自动失效）：

| 场景 | 耗时 |
|------|------|
| 首次构建 | 61.8 秒 |
| 从磁盘缓存加载 | **1.02 秒** |

**加速 62 倍**，后端重启后图谱检索立即可用。

### 4f2.3 图谱检索的实现

```
查询 → 向量匹配图谱实体（复用 BGE-M3，不额外占显存）
     → 沿关系多跳扩展（最多 2 跳）
     → 收集这些实体来源的文本块（chunk_ids）
     → 按跳数衰减打分返回
```

**实体匹配质量实测**：

| 查询 | 匹配到的实体（相似度） |
|------|---------------------|
| 吻合口漏 | 吻合口漏 (1.000)、临床吻合口漏 (0.926)、盆腔吻合口漏 (0.901) |
| 荧光造影评估血供 | 荧光血管造影 (0.725)、术中荧光血管造影 (0.692) |
| 加速康复外科 | 加速康复外科 (1.000)、快速康复外科 (0.915) |

### 4f2.4 图谱的实测贡献（重要发现）

**启用图谱检索后，中文评测集指标显著提升**：

| 配置 | R@1 | R@3 | R@5 | R@10 | MRR | NDCG@5 | 延迟 |
|------|-----|-----|-----|------|-----|--------|------|
| 无图谱 | 0.072 | 0.246 | 0.344 | 0.456 | 0.184 | 0.213 | 591ms |
| **含图谱** | **0.190** | **0.313** | **0.390** | **0.538** | **0.282** | **0.293** | 578ms |
| 图谱+重排 | **0.313** | — | **0.610** | **0.682** | **0.427** | **0.465** | 2154ms |
| **图谱贡献** | **+11.8** | **+6.7** | **+4.6** | **+8.2** | **+9.8** | **+8.1** | 几乎无开销 |

（单位：个百分点。R@1 由 0.072 提升到 0.190，**接近 3 倍**。）

**英文评测集则呈现相反趋势**：

| 配置 | R@1 | R@5 | R@10 | MRR | NDCG@5 |
|------|-----|-----|------|-----|--------|
| 无图谱 | 0.122 | 0.476 | 0.577 | 0.258 | 0.302 |
| 含图谱 | **0.169** | 0.460 | **0.593** | **0.288** | **0.317** |
| **图谱贡献** | **+4.8** | **−1.6** | **+1.6** | **+3.0** | **+1.5** |

**如何解释这一差异（论文要点）**：

实体是**用中文抽取**的（提示词要求翻译为规范中文术语）。
因此：

- **中文查询** → 与中文实体名**同语言匹配**，种子实体质量高，
  多跳扩展带来的关联证据有效。R@1 提升近 3 倍。
- **英文查询** → 需要跨语言匹配中文实体名（依赖 BGE-M3 的跨语言对齐），
  种子实体质量下降，扩展阶段引入更多噪声。
  结果是**排序精度提升（R@1/MRR 上升）但召回略降（R@5 −1.6）**。

**结论**：图谱检索的收益**取决于查询与实体的语言一致性**。
在中文问答场景（本课题的主要使用场景）应启用；
若将来支持英文问答，需要同时抽取英文实体（或改用双语实体名），
否则图谱会从"补充召回源"变成"噪声源"。

> ⚠️ **一个必须记录的排查教训**：早期评测图谱贡献为 **0.0**，
> 与基线完全一致。原因是当时 `SearchRequest.use_graph` 的默认值为 `False`；
> 图谱接入后默认值已改为 `True`。图谱路径代码正确却曾未执行，若不核实"路径是否真的被调用"，
> 就会得出「图谱零贡献」的错误结论。
> **教训：任何消融实验都必须先确认被消融的组件确实执行了。**

## 四之七、影像辅助解读（阶段六）

对应报审表「（一）3 术中影像知识库模块」与「（三）4 影像辅助解读模块」。

### 4g.1 设计取舍：为什么走云端 API 而非本地部署视觉模型

本机 GPU 为 RTX 5060 Laptop 8GB，已被 BGE-M3 与重排模型占用约 3GB。
本地部署 7B 级视觉模型至少需 6~8GB 显存，会与检索模型争抢资源，
导致**高频的问答首字延迟显著上升**；而影像解读是**低频操作**
（用户偶尔上传一张图）。因此调用云端 API：

- 不占显存，检索链路性能不受影响
- 无需维护模型权重（磁盘紧张：C 盘仅剩约 62 GB）
- 智谱 GLM-4V-Flash 免费，额度足够毕设使用

**这是明确的资源分配取舍：本机算力优先保障高频检索链路。**

### 4g.2 三段式链路（核心设计）

```
用户上传术中影像
   ↓ ① VLM 客观描述（只描述看到的，不做诊断）
   ↓ ② 从描述中提取关键词 → 构造检索查询 → 检索知识库
   ↓ ③ LLM 综合：影像所见与文献证据对照，输出带 [n] 引用的解读
```

**为什么必须分三段，而不直接让 VLM 出结论**

云端视觉模型对手术影像的诊断能力不可靠，且其输出**无法溯源**。
若直接展示 VLM 的"诊断意见"，就违背了本系统「可溯源」的核心设计，
也带来医学合规风险。因此本模块定位为**辅助解读**而非诊断：

- VLM 只负责客观描述（解剖部位、可见结构、器械、染色范围）
- **结论部分必须由检索到的文献证据支撑**，并带引用编号
- 输出强制附带合规声明

这与文本问答的抗幻觉设计一致：**先取证，再作答**。

### 4g.3 检索查询构造（一个易被忽视的细节）

检索查询**不应直接用整段影像描述**。描述中含大量泛化表述
（"图像质量良好""无法判读"），会稀释检索信号的语义聚焦度。

实现上按结构化字段抽取（`image_analysis.build_retrieval_query`）：

```
优先使用：解剖部位 → 可见所见 → 特殊染色或标记 → 手术器械与材料
过滤噪声：无法判读 / 清晰 / 良好 / 无 / 未见异常 …
```

### 4g.4 提示词的防幻觉约束

影像解读的提示词与文本问答**不完全相同**，因为输入含**两个可能不吻合的
信息源**（视觉模型描述 vs 文献证据）。关键约束：

> **如果影像描述与检索到的证据并不对应**（例如描述的是腹腔镜视野，
> 而证据讨论的是病理分期），必须明确指出二者不直接对应，
> 不要强行建立关联。

否则模型会把不相关的证据缝合进解读，产生看似合理实则错误的结论。

| `GET /api/cases/manage` | 登录用户查看草稿与管理列表 |
| `POST/PATCH /api/cases` | 新增或编辑病例；公开发布需管理员权限 |
| `DELETE /api/cases/{id}` | 删除病例；管理员权限 |

**实现细节**：

- 按 SHA256 去重，同一张图重复上传返回已有记录，不重复占空间
- **VLM 描述结果缓存**在 `kb_image.vlm_analysis`，避免重复消耗云端额度
- 原图经 `/raw` 端点返回而非塞进 JSON，避免响应体膨胀
- 上传时生成 512 维 RGB 颜色/纹理基线特征，公开影像可通过 `/similar` 做相似检索
- 影像描述会查询病例库，返回已发布的相关病例推荐
- 未配置密钥时返回 **503 + 申请指引**（"未填密钥"是部署常态，非程序缺陷）
- 路由顺序：`/stats` 必须定义在 `/{image_id}` **之前**，
  否则会被路径参数匹配而返回 404

**前端**：`frontend/src/views/ImagesView.vue`（导航「影像解读」）

- 影像网格 + 上传对话框（含本地预览与格式/大小前置校验）
- 详情面板展示**系统的推理链路**：VLM 描述 → 构造的检索查询 → 综合解读

### 4g.6 实测验证与踩坑记录

#### 实测：三段式链路完整跑通

**测试影像**：合成的模拟腹腔镜视野（512×384，含粉红组织块、中央缝线、
绿色荧光区、器械），用于验证链路而非评估医学准确性。

**L1：全冷首次调用**（VLM 23.3s + 检索 76.6s + 综合 12.8s = 113.0s）
**L2：模型热 + 描述走缓存**（检索 2.3s + 综合 12.0s = **14.3s**）

缓存机制生效：`vlm_analysis` 落库（186 字符），第二次解读
**未重复调用视觉模型**，省去 23 秒与一次云端额度消耗。

#### 系统行为验证：证据不足时如实拒绝

这是本次测试最有价值的观察。合成图的绿色区域并**不是**真实的 ICG 荧光，
VLM 正确识别出"无特殊染色或标记"，于是检索到的是术后研究与腹膜转移文献
（与吻合口血供不相关）。系统的反应是：

> 「该描述中**未包含**任何关于组织颜色渐变、荧光显像、灌注边界、
> 搏动性出血或血供优劣的判断信息，因此从该描述本身**无法得出关于
> 吻合口血供状态的任何结论**。」
>
> 「**结论：影像描述与检索到的文献证据之间不存在直接对应关系。**」
>
> 「本影像**不足以支撑**任何关于吻合口血供状态的解读结论。」

**系统没有把不相关的证据缝合进解读，而是明确指出证据缺口。**
这正是 4g.2 中「影像描述与证据不吻合时必须指出」这一提示词约束的效果，
也验证了「辅助解读而非诊断」的合规定位在实现层面确实成立。

#### 踩坑记录

**坑 1：GLM-4V-Flash 的 `max_tokens` 上限是 1024**

初次调用返回 400：

```json
{"error":{"code":"1210","message":"max_tokens参数非法：限制数值范围[1,1024]"}}
```

我传的是 2048（其他多模态模型的常见上限）。**该错误直接失败而非静默截断**，
因此必须在请求前收敛。已实现按模型自动收敛（`MODEL_MAX_TOKENS` 表），
换用上限更高的模型时不需改代码。

**坑 2：检索查询被推测性措辞污染**

首版 `build_retrieval_query` 直接把描述按字段拼接，查询长 184 字符且
含大量推测词：

```
结直肠区域 - 两个粉红色的圆形结构 可能是结肠段 - 一个绿色的圆形结构 ...
```

`可能是` 这类不确定性措辞与文献中的**确定性陈述**（"colon cancer"
"anastomotic leak"）语义不匹配，会稀释检索信号。改进后只保留实体性词汇：

```
结直肠区域 两个粉红色的圆形结构 结肠段 一个绿色的圆形结构 肠管或其他组织 ...
```

（184 → 111 字符，剔除推测词与图像质量描述）

**为什么必须剔除推测词**：VLM 的描述天然带不确定性（"可能是结肠段"），
这是**正确**的表达（它不该假装确定）。但检索需要的**是实体**，
不是 VLM 的置信度表述。两者的需求不同，必须在构造查询时转换。

**坑 3：视觉模型描述不完全稳定**

同一张图两次调用，`【特殊染色或标记】` 字段一次返回"无法判读"、
一次返回"无特殊染色或标记"。语义相近但表述不同。

因此**必须缓存描述**（不能每次重新生成），否则：
- 重复消耗云端额度与 4~23 秒等待
- 同一张图的解读会因描述波动而变化，不利于可复现性

## 四之八、多轮对话管理（阶段七）

对应报审表「（二）5 多轮对话管理模块」。

### 4h.1 核心问题：RAG 检索依赖独立查询，但追问大量使用指代

```
用户：结直肠癌术后吻合口漏怎么处理？
助手：（回答……）
用户：它的发生率是多少？          ← "它" 指什么？
```

若直接把「它的发生率是多少？」送去检索，**语义检索与关键词检索都会失效**
（查询里没有任何医学实体）。这是多轮 RAG 最常见的失败点。

### 4h.2 解决方案：检索前插入查询改写

```
改写前：它的发生率是多少？
改写后：结直肠癌术后吻合口漏的发生率是多少
```

**实测结果**（同批 3 轮对话）：

| 轮次 | 用户提问 | 改写结果 |
|------|---------|---------|
| 1 | 结直肠癌术后吻合口漏怎么处理？ | （独立问题，不改写） |
| 2 | **它的**发生率是多少？ | → `结直肠癌术后吻合口漏的发生率是多少` |
| 3 | **那**该怎么预防？ | → `结直肠癌术后吻合口漏如何预防` |

另一组（术中场景）：

| 轮次 | 用户提问 | 改写结果 |
|------|---------|---------|
| 1 | 术中如何评估肠道吻合口的血供？ | 分期识别为 **intraop** |
| 2 | **那荧光造影**有什么证据支持？ | → `术中吲哚菁绿（ICG）荧光血管造影评估肠道吻合口血供有哪些证据支持` |

第 2 轮的改写尤其体现价值：用户只说"荧光造影"，
改写后补全为"术中吲哚菁绿（ICG）荧光血管造影…"，术语与文献表述对齐，
显著提升检索命中率。

### 4h.3 何时跳过改写（成本与准确率的权衡）

改写本身要消耗一次 LLM 调用（约 0.8~1.6 秒）。不能无脑对所有问题执行。

**采用规则启发式而非再用一次 LLM 分类**：

```
1. 无历史（首轮）            → 不改写
2. 明确的新话题标记           → 不改写（"另外""换个话题"）
3. 含指代词（它/这个/该/那…） → 改写
4. 问题很短（<18 字）         → 改写（短问题通常依赖上下文）
5. 其余                      → 不改写（本身已独立完整）
```

这是「成本 vs 准确率」的权衡：规则会漏判少数需要改写的情况，
但省下一次 LLM 调用。**对交互式系统，延迟很关键。**

### 4h.4 意图识别与分期路由

识别问题的围术期分期（术前/术中/术后/通用）与类型
（知识提问/决策建议/比较/总结），把检索限定在对应分期以提升精度。

**关键设计：低置信度时不用分期过滤**

```python
if confidence < 0.6:
    phase = None   # 不强制过滤
```

原因：低置信度下强制过滤会**漏掉跨分期的正确证据**
（例如问题提到"术后"，但关键证据在通用指南中）。

### 4h.5 会话管理

- 内存实现（`ConversationStore`），带 200 会话上限与 LRU 淘汰
- 每会话保留最近 10 轮，改写时只取最近 3 轮，控制 token 消耗
- **为什么不用 Redis**：会话数据量小，丢失代价仅是用户需重新提问，
  不影响知识库一致性。引入 Redis 会增加部署复杂度而收益有限。
  如需多实例部署，替换 `ConversationStore` 实现即可（接口已隔离）

### 4h.6 为什么把多轮做成独立端点而非给 `/api/qa` 加参数

两者状态语义不同：

| 端点 | 语义 | 用途 |
|------|------|------|
| `/api/qa` | **无状态**单轮 | 评测、脚本、单次查询 |
| `/api/chat` | **有状态**会话 | 交互式对话 |

混在一起会让**评测脚本意外携带上下文，导致评测结果不可复现**。
分开后职责清晰 —— 阶段十的评测正是靠 `/api/qa` 的无状态性才可复现。

### 4h.7 过程透明化

响应中包含 `rewritten_query` 与 `is_followup`，
前端「多轮会诊」页把系统的理解过程显示出来：

```

意图识别:  术中 · 知识提问（置信度 0.95）
```

## 五、关键技术决策（答辩要点）

### 5.1 中文检索：放弃 pg_trgm，改用 bigram + 数组倒排索引

**实测发现**：PostgreSQL 的 `pg_trgm` 扩展**完全忽略非 ASCII 字符**。

```sql
SELECT show_trgm('abc');        -- {"  a"," ab",abc,"bc "}   正常
SELECT show_trgm('结直肠癌');    -- {}                        空集
SELECT similarity('结直肠癌','结直肠癌术后吻合口漏');  -- 0
```

这意味着网上常见的「中文用 pg_trgm」方案在本环境会**静默失效**——不报错，但关键词检索永远返回空。

**采用的方案**：
1. 把中文切成 bigram：`吻合口漏` → `{吻合, 合口, 口漏}`
2. 存入 `text[]` 列并建 GIN 倒排索引
3. 检索时用数组重叠运算符 `&&`（走 GIN 索引），在 Python 中按交集比例打分

**为什么不装 zhparser / pg_bigm**：需要自行编译扩展进 PostgreSQL 镜像，
部署复杂度与答辩演示风险都显著上升。bigram 方案零额外依赖，效果对本课题足够。

**局限性（论文需如实说明）**：bigram 粒度较粗，短查询区分度下降，
已通过「向量检索为主、关键词为辅」的融合策略缓解。

代码位置：`backend/app/core/text_utils.py`

### 5.2 文件存储：本地文件系统而非 MinIO

MinIO 已于 **2025 年 10 月撤下官方 Docker 镜像**（开源社区版停止分发），
`minio/minio` 在 Docker Hub 上已不存在，因此无法按原计划部署。

改用本地文件系统存储，理由：
1. 文献 PDF 与影像通过统一接口读写，不需要 S3 的分布式能力
2. 少一个容器依赖，降低部署与答辩演示的故障面
3. 存储层已抽象为 `StorageBackend` 接口，将来如需对象存储，换实现类即可

代码位置：`backend/app/services/storage.py`

### 5.3 检索模型：宿主 GPU + 懒加载

- **懒加载**：不在启动时载入模型，首次调用才加载（BGE-M3 约 6 秒）。
  这样启动快，且不占用显存影响其他任务。可用 `POST /api/models/load` 预热。
- **必须用本地目录路径加载**：传 `'BAAI/bge-m3'` 会触发 `snapshot_download`
  拉取仓库全部文件，而仓库中 `imgs/.DS_Store` 被镜像站拒绝（403），导致加载失败。
- **8GB 显存策略**：GPU 只跑 BGE-M3 与 reranker（实测峰值 3.36GB），
  大模型与影像解读走云端 API，避免超显存。

代码位置：`backend/app/services/model_registry.py`

## 八、常见问题

**Q: pip 安装报「无法连接到远程服务器」**
系统代理 `127.0.0.1:7899` 失效。使用 `deploy/pip/pip.conf`（见 3.2），
或直接关闭 Windows 系统代理。

**Q: 模型加载报 403 Forbidden，URL 含 `.DS_Store`**
不要传仓库名。必须用本地目录路径 `D:\models\bge-m3`。见 5.3。

**Q: `docker compose up` 报 minio 镜像找不到**
MinIO 官方镜像已下架，本项目已移除该服务，属预期。见 5.2。

**Q: 首次检索耗时很长（数十秒）**
正常现象，是模型加载的一次性开销。可用 `POST /api/models/load` 预热，
之后检索约 0.3 秒。

**Q: `/health` 显示 degraded**
若仅 `LLM 配置` 与 `多模态模型配置` 为 `--`，属正常——这两个密钥阶段四/六才需要。
基础设施（PostgreSQL/Neo4j/Redis/存储）必须全为 `OK`。

| **更新** | `POST /api/admin/kb/collect` | 按 9 个预定义检索式采集（后台任务，返回 202） |
| | `POST /api/admin/kb/search` | 按自定义检索式采集 |
| | `POST /api/admin/kb/vectorize` | 补齐未向量化的文本块 |
| | `GET /api/admin/kb/tasks` `/{job_id}` | 任务进度（前端 2 秒轮询） |
| **版本管理** | `GET /api/admin/kb/batches` `/{id}` | 更新历史与批次详情 |

### 数据模型新增

  kb_update_batch        更新批次（操作类型、检索式、参数、结果计数、耗时、操作人、图谱重建标志）
  kb_document.batch_id   文献来源批次（支持按批次追溯与回滚）
  kb_document.reviewed_by / reviewed_at / review_note   审核记录

### 质量评估的六个维度

实测当前语料的结果：

    规模      444 篇 / 1661 块（向量化完成率 100%）
    时效性    1977–2026，近三年 49 篇（11.0%）
    证据结构  指南 67 / 系统评价 251 / RCT 125 / 队列 157 / 综述 280 / 病例 36 / 其他 745
    分期覆盖  术后 716 / 术中 388 / 术前 300 / 通用 257
    语种结构  17 个语种，中文仅 17 篇
    审核进度  已审核 0 篇（机制此前未启用）

    健康度 0.552，自动生成 5 条维护建议：
      · 仅 0/444 篇完成审核
      · 近三年文献占 11.0%，时效性偏低
      · 指南与系统评价、RCT 合计 23.0%，高等级证据偏少
      · 中文文献仅 17 篇，跨语言检索效果受限
      · 11 篇文献既无 DOI 也无 PMID，无法核验来源

**健康度是各项指标的均值，仅用于快速判断，不参与任何检索决策。**
论文中引用时应说明其定义（经验权重），不可当作绝对标准。

### 后台任务机制

采集 + 向量化是数十分钟级的操作，若放在 HTTP 请求内同步执行会超时。
因此改为**后台线程执行 + 前端轮询进度**：

    POST /api/admin/kb/collect  → 立即返回 202 与 job_id（创建批次记录）
    后台线程执行采集 → 每完成一个检索式更新进度
    前端每 2 秒 GET /api/admin/kb/tasks/{job_id}
    完成后前端刷新文献列表与质量报告

**两级状态存储**：数据库存最终结果（持久、可追溯、重启不丢），
内存字典存实时进度（每秒变化，写库无必要）。
代价是后端重启会丢失进行中任务的进度，但批次记录仍在库中（状态停在 running），
管理员可据此判断需重跑。

**并发控制**：向量化占用 GPU，用一个全局非阻塞锁保证同一时刻只有一个重任务。
第二个请求直接返回 409「已有任务正在执行」，而不是排队 ——
排队会让管理员误以为任务已开始。

### 权限设计（实测确认）

| 操作 | 管理员 | 医师 |
|------|--------|------|
| 查看文献列表 / 详情 | ✅ | ✅ |
| 查看质量报告 | ✅ | ✅ |
| 审核文献 | ✅ | ❌ 403（需 kb:review） |
| 上架 / 下架 | ✅ | ❌ 403（需 kb:update） |
| 彻底删除 | ✅ | ❌ 403（需 kb:delete） |
| 触发采集 / 向量化 | ✅ | ❌ 403 |

**所有写操作仅限管理员。** 审核决定文献是否进入检索池，会直接影响全系统所有
用户的答题依据，属**发布决策**而非个人判断，因此收归管理员。
医师的定位是知识库的使用者与反馈者。

> 迭代记录：第一版接口文档曾把审核写成「医师也能参与」，
> 但权限表的实际配置就是管理员专属。实测返回 403 后，
> **以代码为准修正了文档**，而不是反过来放宽权限 ——
> 发布语料库的决策不应下放给普通使用者。

### 界面上「下架」与「彻底删除」的区分

**下架**（软删除）是主操作：可恢复，历史问答对该文献的引用仍然有效，
只是不再被检索到。
**彻底删除**放在详情对话框内并要求二次警告确认：不可恢复，
且会使历史问答的引用失效，破坏可追溯性。

这样安排的依据是**误删代价不对称**：多留一篇只占少量空间，删错一篇无法还原。

### 更新后必须重建知识图谱

采集完成后，新文献**不会自动进入 Neo4j 图谱** —— 图谱是用旧快照构建的，
图谱检索路径看不到新文献。这一条在界面「更新知识库」页有醒目提示，
批次表也带「图谱待重建 / 已重建」状态列。

完整更新流程是四步：

    # ① 界面操作：按检索式采集（或自定义检索式）
    # ② 界面操作：补齐向量（若采集时未勾选"同时向量化"）
    # ③ 命令行重建图谱（约 1 小时）
    cd D:\AI\RAG_project\backend
    python scripts\build_graph.py build
    # ④ 验证
    python -m app.etl.cli stats
    python scripts\build_graph.py stats

## 语料结构优化：中文文献与时效性

### 问题诊断

初始采集的 9 个检索式**既无时间过滤、也无语言过滤**（`mindate=None`，
检索式中没有 `[PDAT]` 与 `[lang]`）。后果经实测确认：

    初始 444 篇中：中文文献仅 17 篇（3.8%）
                   近三年文献仅 49 篇（11.0%）

PubMed 默认按**相关度**排序，老文献积累的引用更多、相关度评分更高，
于是被大量纳入；加上没有语言过滤，中文文献自然占比极低。

**这是采集策略缺陷，不是数据源限制。** 实测 PubMed 上的实际可得量：

| 查询 | 可得数量 |
|------|---------|
| 加中文语言过滤 | 1531 篇 |
| 中文 + 近三年 | 297 篇 |
| 全部中文结直肠 + 2020 起 | 1153 篇 |
| 中文指南/共识（直肠癌） | 166 篇 |
| 中文综述/Meta分析 | 432 篇 |
| 中文 RCT | 168 篇 |
| 近三年 RCT / 系统评价 / 指南 | 各 1000+ 篇 |

### 关于「中文文献的题录是英文」

PubMed 对非英文文献提供**英文译名与英文摘要**（题名以方括号标注），实测样本：

    lang=chi | year=2024 | [Cancer incidence and mortality in China, 2022].
    lang=chi | year=2023 | [Surgical skills and precautions of pelvic exenteration ...

这对本系统**反而有利**：向量模型与关键词检索都能正常编码英文摘要，
不会因为中文摘要而失效（中文摘要用 BGE-M3 编码虽可行，但英文摘要
与英文文献语料在同一语义空间，跨语言检索更稳定）。
同时 `language=chi` 元数据保留了「这是中文文献」这一事实，
可用于语种结构统计与中文引用偏好。

### 解决方案

## 中文语料的真实情况与人工录入方案

### 一个必须写清楚的限制

系统主要文献源为 PubMed。**实测确认 PubMed 对非英文文献不提供任何中文文本**：

```
取样 200 篇 language=chi 的文献，直接检查原始 HTTP 响应
  原始响应中的汉字总数 : 0
  含汉字的文献数      : 0
```

验证脚本：`backend/scripts/probe_pubmed_has_chinese.py`（可复核）

因此：

  - `language=chi` 元数据**是准确的**（表示原文语种为中文）
  - 但题名与摘要**均为英文**（题名带方括号 `[...]` 即为英文译名）
  - 语料中不存在中文文本，中文提问只能依靠向量模型的**跨语言能力**匹配，
    无法做中文字面匹配

补充采集 408 篇中文文献后，全库 4948 个文本块中仅 10 个含中文字符（0.2%），
**且全部来自手工录入的种子文献**。这是本系统在中文场景下的真实约束，
应在论文中如实说明。

### 解决方案：人工录入中文指南

指南与共识是最高等级证据，篇幅可控、结构清晰，适合人工录入。
为此新增 `app/etl/manual_import.py` 与 `data/manual/` 目录。

**为什么用 Markdown 文件而不是内联在代码里**

早期实现（`seed_references.SeedReference`）把中文摘要写在 Python 源码字符串里，
对短摘要可行，但录入指南正文会遇到三个问题：
  1. 指南正文数千至数万字，塞进代码字符串无法阅读与校对
  2. 指南有章节结构，内联字符串会丢失结构，切块时无法按章节切分
  3. 医学文本需多人复核，代码文件不适合作为校对载体

**文件格式**

    # 指南标题

    **作者**：编写组
    **期刊**：中华肿瘤杂志
    **年份**：2020
    **分期**：general

    ## 章节名

    正文段落……

**约定**：文件名以下划线开头的（`_模板.md`、`_录入清单.md`）是参考资料，
不参与导入；README.md 同理。

**导入命令**

    cd D:\AI\RAG_project\backend
    $env:PYTHONPATH = "D:\AI\RAG_project\backend"
    & "D:\deep seek test\rag-venv\Scripts\python.exe" -m app.etl.cli manual --dry-run   # 预览
    & "D:\deep seek test\rag-venv\Scripts\python.exe" -m app.etl.cli manual              # 导入

### 三项配套改进

**① 标题去重（修 bug）**

原 `_find_existing` 只按 PMID/DOI 去重。人工录入的指南两者皆无，
**每次重复导入都会新建一条记录** —— 而指南需要反复校对增补，
重复导入是高频操作。已补充按标题归一化匹配
（忽略全角半角括号、空格、标点差异），实测重复导入为 `新增 0 / 更新 1`。

**② 分期/证据等级可人工声明**

分类器按关键词匹配，对跨阶段内容会误判。实测
《中国结直肠癌筛查与早诊早治指南》被判为 `postop`（置信度 0.60），
而筛查指南应属 `general`。

已支持录入者在元数据中声明分期与证据等级并覆盖分类器结果，
**覆盖仅对人工录入生效**（`phase_hint` 只由 `manual_import` 设置），
PubMed 文献继续走纯自动标注，保证既有评测结果可比。
标注依据会明确区分 `[人工声明]` 与 `[自动标注]`。

**③ 中文摘要解析（为将来接入中文源预留）**

解析器现在会把 PubMed 记录中并列的中文 `AbstractText` 段单独存入
`ParsedArticle.abstract_zh_sections`。

> ⚠️ 修复过程中发现一个隐蔽 bug：CJK 正则误用了 raw string
> `r"[\u4e00-\u9fff]"`，Python 不会解析其中的 `\u4e00`，
> 正则实际在匹配字面串 `u4e00`~`u9fff`。
> 症状是解析器取到 0 篇中文摘要，而 `_has_cjk("吻合口漏")` 恰好返回 True
> （5 个汉字的码点落在那段字面区间内），使 bug 更难发现。
> 正确写法是去掉 `r` 前缀：`re.compile("[\u4e00-\u9fff]")`。

### 实测效果

导入《中国结直肠癌筛查与早诊早治指南（2020，北京）》7 个章节（977 字）后：

| 中文提问 | 第 1 名命中 | 相关度 |
|---------|-----------|--------|
| 结直肠癌筛查从多少岁开始？ | 筛查的年龄起点与终止年龄 | 1.149 |
| 结肠镜检查的退镜时间要求是多少？ | 筛查方法：结肠镜 | 1.136 |
| 林奇综合征家系何时开始筛查？ | 遗传性结直肠癌的筛查 | 1.137 |

**每章成为一个检索单元**，章节名参与检索，命中后可直接定位到具体推荐意见。

### 下一步

`data/manual/_录入清单.md` 按四个围术期分期列出了建议录入的指南清单
（标注优先级），共约 30 项。录入后重新执行 `manual` 导入即可生效。

### 安全机制

**用「下架」而非删除**：`is_active=False` 后检索链路立即不再使用
（`search_repo._base_query` 中有 `Document.is_active.is_(True)`），
但文本块与向量完整保留（下架的 4483 个块仍在库中）。

**执行前快照**：`data/eval/corpus_active_snapshot_<时间戳>.json`
记录操作前上架的全部 1264 篇 id。

**恢复方式**（两种）：

    # 脚本恢复（适合批量）
    cd D:\AI\RAG_project\backend
    python scripts\restore_corpus.py --list          # 查看可用快照
    python scripts\restore_corpus.py --latest --dry-run   # 预览
    python scripts\restore_corpus.py --latest             # 执行

    # 界面恢复（适合个别文献）
    知识库 → 文献管理 → 筛选「已下架」→ 勾选 → 批量上架

**审计留痕**：操作写入 `sys_audit_log`（action=`prune_corpus`）。

### 相关脚本

    backend/scripts/plan_corpus_prune.py    生成选材计划（只读，输出决策明细）
    backend/scripts/apply_corpus_prune.py   执行精简（复用选材逻辑，保证一致）
    backend/scripts/restore_corpus.py       按快照恢复

**三个脚本共用同一套评分逻辑**（apply 通过 import 复用 plan 的函数）。
若两处逻辑不一致，会出现「计划保留 A、实际下架 A」这类严重错误。

## 启动器如何找到 Python

双击 `start.bat` 时，`start-all.ps1` 按以下顺序找解释器并**逐个验证依赖**
（`import fastapi, torch`）：

1. `start-all.ps1 -PythonPath <路径>` 或环境变量 `RAG_PYTHON`
2. 根目录 `launcher.config.json` 的 `python` 字段
3. 项目内 `.venv` / `venv` / `backend\.venv` / `backend\venv`
4. PATH 中的 `python`

没有现成虚拟环境时，在 `launcher.config.json` 写明路径即可：

```json
{ "python": "D:\\path\\to\\venv\\Scripts\\python.exe" }
```

只检查不启动：`start.bat -CheckOnly`。
