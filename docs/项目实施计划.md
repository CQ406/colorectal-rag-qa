## 零、总体判断

| 维度 | 评估 |
|------|------|
| 工作量 | **偏重但不是偏难**。四大模块共 18 个子模块，属毕设正常偏上水平 |
| 技术风险 | **低**。全部技术选型均为成熟开源方案，本机环境已验证可跑通 |
| 最大风险 | **进度风险**，不是技术风险。知识图谱与评测集最容易拖期 |
| 建议周期 | **16 周**（含论文写作），核心功能在第 10 周即可演示 |
| 关键策略 | **先跑通端到端最小闭环，再逐模块加深**。绝不要按模块顺序逐个做完再联调 |

**核心原则**：第 5 周必须有一个"能输入问题、能返回带引用的答案"的可运行系统，哪怕很粗糙。之后所有工作都是在这个闭环上加深。这是毕设项目不烂尾的唯一可靠做法。

## 二、系统架构

```
┌──────────────────────────────────────────────────────────────┐
│  前端 Vue 3 + Element Plus + Vite                            │
│  问答对话 │ 引用溯源跳转 │ 影像上传 │ 知识库管理 │ 监控看板      │
└──────────────────────────┬───────────────────────────────────┘
                           │ REST + SSE 流式
┌──────────────────────────▼───────────────────────────────────┐
│  后端 FastAPI :8000                                           │
│                                                               │
│  ┌─────────────────── 问答编排（核心） ──────────────────┐    │
│  │ 意图识别 → 域路由(术前/术中/术后) → 多路召回           │    │
│  │   ├─ 文本向量检索（pgvector HNSW）                    │    │
│  │   ├─ 关键词检索（PG 全文 / BM25 近似）                │    │
│  │   └─ 知识图谱路径检索（Neo4j Cypher）                 │    │
│  │ → RRF 融合 → bge-reranker 精排 → 提示词组装            │    │
│  │ → LLM 生成（DeepSeek API，SSE 流式）→ 引用溯源         │    │
│  └───────────────────────────────────────────────────────┘    │
│                                                               │
│  ┌─ 知识库管理 ─┐ ┌─ 影像解读 ─┐ ┌─ 用户权限 ─┐ ┌─ 日志监控 ─┐ │
│  └──────────────┘ └────────────┘ └────────────┘ └────────────┘ │
└──┬──────────┬──────────┬───────────┬──────────┬──────────────┘
   │          │          │           │          │
┌──▼───┐ ┌───▼───┐ ┌────▼────┐ ┌────▼────┐ ┌──▼─────────────┐
│PG16  │ │Neo4j 5│ │Redis 7  │ │MinIO    │ │GLM-4V-Flash    │
│pgvec │ │ 图谱  │ │缓存/会话 │ │文件存储 │ │DeepSeek API    │
└──────┘ └───────┘ └─────────┘ └─────────┘ └────────────────┘
        BGE-M3 + reranker 在宿主 GPU 上（不走容器）
```

**关键设计决策**（答辩会被问，先想清楚）：

1. **向量库用 pgvector 而非 Milvus**：规模（20 万块）够用，向量/元数据/全文检索同库同事务，多路召回一次 SQL 写完。你镜像里虽有 milvus，但那需要 etcd + MinIO 三件套，运维成本高，**不建议本课题用**。
2. **检索模型在宿主 GPU、服务在容器**：避免容器内 GPU 直通复杂度。用 FastAPI 单开一个 `/embed` 内部服务即可。
3. **LangChain LCEL 显式编排，检索算法保持透明**：2026-11-08 已迁移主问答编排；RRF 融合、重排、引用解析仍由项目模块实现，通过命名 Runnable 阶段调用。
4. **影像解读走云端 API**：报审表已明确这一条，且本机 8GB 显存装不下视觉模型。

## 三、十大阶段与里程碑

### 阶段一：项目骨架与基础设施（第 1 周）

**目标**：一条命令拉起全部依赖服务，后端能返回健康检查。

| 步骤 | 产出 | 验收标准 |
|------|------|----------|
| 1.1 建项目目录结构 | `backend/ frontend/ etl/ deploy/ tests/ docs/` | 结构清晰，README 说明各目录用途 |
| 1.2 写 `docker-compose.yml` | PG16+pgvector、Neo4j、Redis、MinIO | `docker compose up -d` 后 4 个服务 healthy |
| 1.3 后端骨架 | FastAPI + 分层（api/service/repo/model） | `GET /health` 返回各依赖连通状态 |
| 1.4 配置管理 | `.env` + pydantic-settings | 密钥不入库，`.env.example` 提供模板 |
| 1.5 数据库迁移 | Alembic 初始化 | `alembic upgrade head` 建表成功 |

**里程碑 M1**：`docker compose up -d && uvicorn app.main:app` 一条命令起系统，`/health` 全绿。

> 注意：你的 WSL 内存限制是 12GB。PG(1G) + Neo4j(2G) + Redis(0.5G) + MinIO(0.5G) 约 4GB，余量充足。

### 阶段二：知识数据采集与入库（第 2~3 周）

**目标**：把报审表那 15 篇文献 + PubMed 抓取的文献变成库里的文本块。

| 步骤 | 技术 | 产出 |
|------|------|------|
| 2.1 PubMed 采集器 | `requests` + E-utilities API | 按关键词抓题录+摘要，支持增量与去重（按 PMID） |
| 2.2 15 篇种子文献入库 | 手工/脚本录入 | 作为首批权威语料，含指南与规范 |
| 2.3 PDF 解析 | PyMuPDF + pdfplumber | 抽取正文、章节标题、页码、表格 |
| 2.4 复杂版面解析 | MinerU（备用） | 处理双栏/表格较多的指南 PDF |
| 2.5 文本切分 | 递归字符切分 + 语义边界 | 512 token 块 + 64 overlap，保留章节元数据 |
| 2.6 元数据入库 | SQLAlchemy | 题录、来源、年份、证据等级、术前/术中/术后标签 |
| 2.7 后台任务 | Celery + Redis 或 APScheduler | 批量入库可断点续跑，**不阻塞 API** |

**关键设计**：每个 chunk 必须携带 `doc_id / 章节 / 页码 / 证据等级 / 分期标签`。**没有元数据就没有引用溯源**，这是阶段四的前提，不能省。

**里程碑 M2**：库中 ≥ 2000 个文本块，来自 ≥ 200 篇文献，全部分期标签完整。

---

### 阶段三：RAG 检索链路（第 4~5 周）⭐ 核心

**目标**：问一句话，能召回正确段落。

| 步骤 | 技术 | 产出 |
|------|------|------|
| 3.1 向量化服务 | FlagEmbedding + 本机 GPU | `/embed` 内部接口，batch 32~64，694 条/秒 |
| 3.2 向量存储 | pgvector，HNSW 索引，1024 维 | `kb_chunk.embedding`，余弦距离 |
| 3.3 向量召回 | SQL + pgvector | top-50 |
| 3.4 关键词召回 | PG 全文检索 / BM25 近似 | top-50（中文需 zhparser 或 pg_bigm） |
| 3.5 RRF 融合 | 手写倒数排名融合 | 两路结果合并去重 |
| 3.6 重排 | bge-reranker-v2-m3 | top-50 → top-5，105 对/秒 |
| 3.7 检索接口 | FastAPI | `POST /api/search` 返回带分数与元数据的段落 |

**里程碑 M3**：`/api/search` 对 20 道测试问题，正确段落出现在 top-5 的命中率 **≥ 70%**。

> 这是全项目最关键的一步。M3 达成即意味着毕设"能不能做出来"已经确定，后面都是加分项。

### 阶段四：答案生成与引用溯源（第 6 周）⭐ 核心

**目标**：端到端闭环——提问得到带引用的答案。

| 步骤 | 技术 | 产出 |
|------|------|------|
| 4.1 LLM 接入 | DeepSeek API（OpenAI 兼容） | 统一 `llm_client`，支持重试与超时 |
| 4.2 提示词工程 | 模板 + 证据约束 | 明确要求"仅依据给定证据回答，无依据则说明" |
| 4.3 流式输出 | SSE | 前端逐字显示，体验达标 |
| 4.4 引用标注 | 结构化输出（JSON） | 答案标注 `[1][2]` 并映射到 chunk_id |
| 4.5 溯源接口 | FastAPI | `GET /api/citation/{chunk_id}` 返回原文片段+页码 |
| 4.6 置信度提示 | 重排分数映射 | 低分结论显式提示"证据不足" |

**里程碑 M4（最重要）**：完整闭环跑通——**输入问题 → 返回答案 + 可点击引用 → 跳转原文片段**。

按期到达 M4，毕设就及格了。之后每个阶段都是在加分。

### 阶段五：知识图谱模块（第 7~8 周）

| 步骤 | 技术 | 产出 |
|------|------|------|
| 5.1 本体设计 | ICD-10 + 自定义 schema | 疾病/术式/并发症/药物/症状 五类实体及关系 |

**里程碑 M5**：图谱可视化（Neo4j Browser 截图入论文）+ 图检索接入问答链路。

## 六、论文可用的创新点（提前布局）

不要等写论文时才想"我的创新是什么"。建议围绕这四点做实验设计：

1. **领域知识图谱增强的混合检索**——文本向量 + 关键词 + 图谱路径三路召回，用消融实验证明每路的贡献。
2. **围术期分期感知的检索域过滤**——按术前/术中/术后路由，减少跨期噪声，可对比"不做分期过滤"的提升幅度。
3. **证据等级与引用溯源机制**——答案标注来源与证据等级，用引用准确率量化。
4. **低资源硬件下的检索侧 GPU 加速方案**——实测 694 条/秒 vs CPU 的对比，8GB 显存下的部署策略（这是工程贡献，答辩好讲）。

## 七、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| **知识图谱拖期** | 挤占评测时间 | 规模严格控制，第 8 周末必须收尾，超期就砍到"仅核心五类实体" |
| **PDF 解析质量差** | 检索命中率低 | 优先用 PubMed 结构化摘要；指南类 PDF 人工校对关键章节 |
| **中文全文检索** | 关键词召回效果差 | 装 zhparser 扩展，或改用 pg_bigm；实在不行先用向量单路跑通 |
| **评测集标注耗时** | 无实验数据 | 用 LLM 预标注 + 人工校对，效率可提升 3 倍；第 12 周就启动标注 |
| **API 费用或限流** | 演示中断 | 缓存高频问答结果；准备离线演示模式 |
| **本地模型幻觉** | 答案错误 | 生成一律走云端大模型，本地只做检索（已定方案） |
| **C 盘再次告急** | 系统异常 | 已迁 Docker 到 D 盘 + `.wslconfig` 限制；新数据一律放 D 盘 |
