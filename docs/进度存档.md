### 2. 中文语料问题：**没有解决**，这是本质限制 ⚠️

**实测确认：PubMed 对非英文文献不提供任何中文文本。**

```
取样 200 篇 language=chi 的文献，直接检查原始 HTTP 响应
  原始响应中的汉字总数 : 0
  含汉字的文献数      : 0
```

验证脚本：`backend/scripts/probe_pubmed_has_chinese.py`（可复核）

因此那 408 篇「中文文献」：
- `language=chi` 元数据**是准确的**（表示原文语种为中文）
- 但**题名与摘要全是英文**（题名带方括号 `[...]` 即英文译名）
- **语料里没有中文文本**，中文提问只能靠向量模型跨语言匹配

全库 4948 个文本块中仅 10 个含中文字符（0.2%），**全部来自手工录入的种子文献**。

## 重大修正（PDF 抽取）

### 发现一个灾难性 bug

早期抽取流程的 `merge_wrapped_lines` **反复扫描并合并行直到不再变化**。
当某行结尾既不是句末标点、也不是标题时，它会与下一行合并；
合并后的行**仍不满足**结束条件，继续合并 —— **一路吞掉整篇文档**。

实测后果：

| 文件 | 旧方法 | 修正后 | 提升 |
|------|--------|--------|------|
| 直肠肿瘤三维可视化指导精准手术专家共识（2025版） | **178 汉字** | 10,550 | **59 倍** |
| 结直肠癌肝转移诊断和综合治疗指南（2025版） | **1,149 汉字** | 16,349 | **14 倍** |

### 而我的「防御措施」放大了危害

`clean_draft.py` 里我加过一段「防御性截断」：

    if len(para) > 4000:
        para = para[:4000] + "……（本段过长已截断，请核对原文）"

当合并失控产生万字符巨行时，**这段截断直接把内容删掉了**。
防御措施本身成了破坏源。

### 修正方案：改用 PDF 版面块

新增 `scripts/extract_by_blocks.py`，用 `page.get_text("blocks")` ——
PDF 解析器已完成的版面分析，块边界即段落边界，**不再猜标点**。

关键约束：**块内可合并行，块边界不可跨越**。

同时处理分栏：按 x 坐标把块分到左右栏，栏内按 y 排序，栏间按阅读顺序。

### 全量对照结果（41 份 PDF）

| 指标 | 旧方法 | 新方法 |
|------|--------|--------|
| 总汉字 | 394,969 | **407,024** |
| 大幅修复（≥3倍） | — | 2 篇 |

**重要更正**：此前报告的「29 篇评级为差」是**评级标准误导** ——
按「最长行长度」和「汉字占比」判定，而巨长行并不等于丢内容。
实际只有 2 篇真正灾难性丢失。

## 修复：文献语种分类错误

### 现象

知识库管理页里，34 篇英文全文全部被标成「中文*」。

### 根因

`app/etl/manual_import.py` 的 `to_parsed_article` 把语种**硬编码为 "chi"**：

    language="chi",

人工录入通道原为中文指南设计，后来用于导入英文全文时，

1. 元数据显式声明 `**语种**：zh/en` → 以声明为准

## 修复：检索报 NaN not allowed in vector

### 现象

问答页面报「生成失败」，展开是一长串 SQL 错误：

    (psycopg.errors.DataException) NaN not allowed in vector
    ... WHERE kb_document.is_active IS true AND kb_chunk.embedding IS NOT NULL
    [parameters: {'embedding_1': '[nan,nan,nan,...]'}]

### 根因

**查询向量全是 NaN**，pgvector 拒收 NaN 向量。

模型以 **fp16** 加载（`use_fp16=(device=="cuda")`）。fp16 在部分 GPU/驱动组合下
会数值溢出，`encode` 返回 NaN。实测该后端进程运行一段时间后，
**所有**查询向量都变成 NaN；重启进程即恢复 —— 说明是进程内模型状态问题，
不是数据或代码逻辑问题。

### 修复（两层）

**1. 自愈：检测到 NaN 时自动切 fp32 重载重试**

`search_service.embed_texts` 是所有向量的唯一入口，在此加数值校验：

    校验 dense_vecs 是否全为有限值
      → 发现 NaN：registry.reload_embedder(force_fp32=True) 后重试一次
      → 仍失败：抛 EmbeddingInvalidError

`model_registry` 新增 `reload_embedder(force_fp32=...)`，
可在**不重启进程**的前提下切换精度重载。

**2. 报错收敛：不再把 SQL 异常抛给用户**

API 层把 `EmbeddingInvalidError` 映射为 HTTP 503，
提示「向量模型输出异常（含 NaN），已尝试切换 fp32 仍未恢复…」，
并给出可选处置（重启后端 / 设 MODEL_FORCE_CPU / 降低 embedding_max_length）。

涉及文件：
- `app/services/model_registry.py`（精度设置 + reload_embedder）
- `app/services/search_service.py`（NaN 校验 + fp32 重试 + EmbeddingInvalidError）
- `app/api/v1/search.py`、`app/api/v1/qa.py`（503 映射）

### 验证

重启后端后：

    检索 「加速康复外科的核心措施有哪些？」 → 200，3 条相关结果
    问答 「吻合口漏怎么预防？」           → 200，5 条引用，无效引用 0

49 项单元测试通过。

### 运维建议

若该现象反复出现，在 .env 设 `MODEL_FORCE_CPU=true` 强制 CPU 编码
（更慢但稳定），或降低 `embedding_max_length`。

右侧引用卡片点「展开原文」，只比折叠时多显示一点，仍看不到整段原文。

### 根因

后端 `citation._snippet()` 把原文**截断到 300 字**后才放进 `content_snippet`：

    def _snippet(content: str, max_len: int = 300) -> str:

前端「展开原文」只是解除 CSS 的 3 行限制（`-webkit-line-clamp`），
显示的仍是那 300 字，**永远看不到 300 字之后的内容**。

### 修复

**后端**新增 `GET /api/chunks/{chunk_id}` 返回完整原文与位置信息
（章节、页码、字数、所属文献是否上架）。
`search_repo.get_chunk_with_doc()` 不限制文献是否上架 ——
被引用过的块即使后来下架也应可查，否则历史答案的引用会失效。

该端点加入公开白名单（与 `/api/search` 一致）：
检索本身公开，单独拦全文没有意义，反而让未登录用户展不开引用。

**前端**：

- `CitationPanel` 展开时按 `chunk_id` 调该接口，取回后缓存（`fullText`）
- 展开后显示「N 字 · 全文 / 正在取全文… / 仅摘要」
- 取全文失败时静默退回摘要，不打断阅读

## 多轮会诊：新增「停止生成」按钮

### 现状

「智能问答」页早有停止生成（`QaView` 的按钮 → store `abort()`），
「多轮会诊」页没有 —— 两页体验不一致。

### 实现

`ChatView` 输入区在 `busy` 时把「发送」换成红色「停止生成」：

    <el-button v-if="busy" type="danger" plain @click="stopGeneration">
      <el-icon><CircleClose /></el-icon> 停止生成
    </el-button>
    <el-button v-else type="primary" @click="send">发送</el-button>

`stopGeneration()` 做三件事：

1. 调 `abortChat()` 中断 fetch
2. 把当前助手消息标为 `aborted`，保留已收到的增量内容
   （全部为空时才写入「（已停止生成）」——医学回答看一半也比没有强）
3. **主动 resolve 挂起的 Promise**

### 一个必须处理的隐患

`ssePost()` 在 `AbortError` 时只是静默返回，**不会回调 `onDone`/`onError`**。
而 `send()` 里是 `await new Promise(...)` —— 于是该 Promise 永不落地，
`finally` 不执行，`busy` 一直为 true，按钮会卡在「推理中」再也点不动。

因此新增 `pendingResolve` 保存 resolve 函数，由停止流程与「新会话」主动调用。
「新会话」也要 resolve 同理（虽然按钮在生成中被禁用，但流程上不能留死锁）。

### 验证

`vue-tsc --noEmit` 退出码 0；`vite build` 退出码 0。

## 多轮会诊：切换页面后对话被清空

### 现象

在多轮会诊里对话几轮，切到「知识库」等其它页面再回来，**对话内容全没了**。

### 根因

`ChatView` 的 `turns` 与 `sessionId` 都是**组件内部状态**，
路由切换时组件卸载、状态随之销毁；后端会话其实还在内存里，只是前端没去取。

### 修复

**前端**：用 `sessionStorage` 记住会话 ID，返回页面时按 ID 拉回历史重建列表。

- `SESSION_KEY = 'cr.chat.session_id'`
- `onMeta` 收到 `session_id` 时立即写入（**生成中途切走也能恢复**）
- `onMounted` 调 `restoreSession()`：`GET /api/chat/{sid}` → 逐轮重建 user/assistant 消息
- 会话已过期（后端重启或超 TTL）返回 404 → 清掉本地 ID，避免每次进来都请求失败
- 「新会话」同时清除本地 ID，否则刚清空又被拉回来

用 `sessionStorage` 而非 `localStorage`：关掉标签页即失效，
与后端「会话存内存、重启丢失」的生命周期匹配。

**后端**：会话历史原先只存 `citations_count`（条数），不存引用明细。
若只恢复文本，答案正文里有 `[1][2]` 标记、右侧面板却显示「未引用任何文献」，自相矛盾。
因此：

- `ConversationTurn` 增加 `citations: list`
- `chat()` 与 `chat_stream()` 写入 `qa_result.citations` / `final_citations`
- `ChatTurnItem` schema 增加 `citations: list[dict]`

### 验证

    GET /api/chat/{sid}
      turn_count=2
      [1] 加速康复外科的核心措施有哪些？ | 引用 4 条 | 首条: 结直肠微创外科术式…
          chunk_id=702d2e60… sections=二、结直肠微创外科新设备
      [2] 它的证据等级高吗？ | 引用 5 条 | 首条: 2025版加速康复外科结直肠手术指南…

引用明细含 `chunk_id`，因此恢复后「展开原文」同样可用。

`vue-tsc --noEmit` 退出码 0；后端 49 项单元测试通过。

### 遗留限制

会话仍存在后端内存（上限 200 个，LRU 淘汰；进程重启即失效）。
届时前端会检测到 404 并清掉本地记录，用户需要重新提问。
如需跨重启保留，需要把 `ConversationStore` 换成 Redis 或数据库实现（接口已隔离）。

## 修复：识别不了「你是谁」这类助手指令问题

### 现象

在多轮会诊问「你是谁」，系统判为「知识提问（置信度 0.10）」，
走完整检索链路后答出：

    提供的资料中未包含与"我是谁"或助手身份设定相关的信息，因此无法依据证据片段回答…

属答非所问。

### 根因

意图分类只有四类（知识提问／决策建议／比较／总结），**缺「助手指令」这一类**。
「你是谁」「你能做什么」「怎么用」不该检索，应直接以系统自身身份回答。

### 修复

新增 `app/services/meta_intent.py`：

- `is_meta_question(q)`：按正则识别身份、能力、用法、边界四类问法
  （限制长度 ≤30 字，避免把含具体临床内容的长问题误判）
- `build_meta_answer(doc_count, chunk_count)`：生成自我介绍，写清
  **能做什么 / 不能做什么 / 怎么问更好**，并带上当前语料规模

接线四处（覆盖两个页面各自的流式与非流式入口）：

| 位置 | 覆盖 |
|------|------|
| `rag_service.answer` | `/api/qa` |
| `rag_service.answer_stream` | `/api/qa/stream`（智能问答页实际使用） |
| `conversation.chat` | `/api/chat` |
| `conversation.chat_stream` | `/api/chat/stream`（多轮会诊页实际使用） |

短路时：不发 LLM、不检索、引用为空、`intent="meta"`、置信度 1.0。

前端 `INTENT_LABELS` 增加 `meta: '助手指令'`，界面不再显示原始英文。
