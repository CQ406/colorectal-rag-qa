# 第一部分 基础层

## 1. 配置与基础设施

**职责**：集中管理全部可调参数，区分部署级配置与运行时配置。

**实现**：`app/core/config.py`（293 行）。用 pydantic-settings 定义多个配置类
（AppSettings / PostgresSettings / LLMSettings / RetrievalSettings / AuthSettings…），
由 `Settings` 聚合，通过 `settings.retrieval.vector_weight` 这类路径访问。

**两层配置结构**

    环境变量（.env）     部署级默认值，重启生效
          ↓ 启动时写入
    配置表（sys_config） 运行时可调，改完立即生效

**为什么需要运行时配置**：检索权重必须按实际语料反复调试。
后端启动含模型加载（约 60 秒），若每次调参都要改 .env 并重启，调试成本无法接受。

**实测踩坑**：`AuthSettings` 曾漏写 `env_file`，导致 `.env` 里配了密钥却读到空值。
做了对照实验确定规则：

| env_file | env_prefix | 结果 |
|----------|-----------|------|
| 有 | 有 | ✅ 读到 |
| 有 | 无 | ❌ 空 |
| 无 | 有 | ❌ 空 |

**两者必须同时存在**。

## 2. 数据库与缓存

**职责**：持久化文献、文本块、向量、图谱、用户、日志。

| 存储 | 用途 | 关键点 |
|------|------|--------|
| PostgreSQL 16 | 文献题录、文本块、向量、用户、日志 | 启用 pgvector 0.8.7 |
| Neo4j 5.26 | 知识图谱 | 1423 节点 / 1380 关系 |
| Redis 7.4 | 缓存 | — |

**表结构**

    kb_document      文献题录（含摘要、元数据、审核状态、来源批次）
    kb_chunk         文本块（检索最小单元：内容 + 向量 + bigram 数组）
    kb_image         影像资产（含 VLM 解读缓存）
    sys_user         用户账号
    sys_audit_log    审计日志
    sys_qa_log       问答日志
    sys_qa_feedback  人工反馈
    sys_config       运行时配置
    kb_update_batch  知识库更新批次（版本管理）

**索引设计的关键决策**

1. **向量索引**：pgvector HNSW，1024 维
2. **中文检索索引**：`bigrams` 数组 + GIN 倒排索引
3. **不建 pg_trgm 索引**——实测 `show_trgm('结直肠癌')` 返回空集，
   pg_trgm 完全忽略非 ASCII 字符，对中文静默失效

## 3. 模型注册与管理

**职责**：惰性加载检索模型，避免启动时占用显存。

**实现**：`app/services/model_registry.py`（187 行）。

**为什么惰性加载**：两个模型（BGE-M3 + bge-reranker-v2-m3）合计占用数 GB 显存。
若启动时加载，会拖慢启动并影响其他任务；服务空闲时也白占显存。

**实测数据**

| 模型 | 加载耗时 | 说明 |
|------|---------|------|
| BGE-M3 | 4.4 秒 | 向量编码 |
| bge-reranker-v2-m3 | 5.7 秒 | 交叉编码器重排 |

**首次提问会等待约 60 秒**（含模型下载校验与预热），因此提供
`POST /api/models/load` 供演示前预热。

# 第二部分 知识入库层（离线）

## 4. 文献采集

**职责**：从 PubMed 批量采集文献题录与摘要。

**实现**：`app/etl/pubmed_client.py`（415 行）、`collect_queries.py`、
`collect_queries_supplement.py`（211 行）。

**限流处理**：PubMed 无 API key 时限 3 次/秒，有 key 时 10 次/秒。
模块通过请求间隔控制速率，并在 429/5xx 时指数退避重试。

**两组检索式**

| 组 | 数量 | 覆盖 |
|----|------|------|
| 主检索式 | 9 条 | 术前 / 术中 / 术后 / 通用 |
| 补充检索式 | 17 条 | 中文文献 9 条 + 近三年高证据 8 条 |

**关键的踩坑与修正**

初始 9 条检索式**既无时间过滤、也无语言过滤**（`mindate=None`，
检索式中无 `[PDAT]` 与 `[lang]`）。后果：PubMed 按相关度排序，
老文献引用多、相关度高，被大量采入。

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 中文语种文献 | 17 篇（3.8%） | 408 篇（32.3%） |
| 近三年文献 | 49 篇（11.0%） | 495 篇（39.2%） |

**一个重要的负面发现**：PubMed 对非英文文献**不提供任何中文文本**。

    取样 200 篇 language=chi 的文献，直接检查原始 HTTP 响应
      原始响应中的汉字总数 : 0

验证脚本：`backend/scripts/probe_pubmed_has_chinese.py`

因此「中文文献占比」只表示**原文语种**，不代表库里有中文文本。
真正的中文语料必须靠人工录入（见第 7 节）。

## 5. 文档解析与切分

**职责**：把文献题录切分为可检索的文本块。

**实现**：`app/etl/chunker.py`（181 行）、`app/etl/ingest.py`（328 行）。

**切分策略**

    Title         标题单独成块（标题蕴含核心主题，对检索有价值）
    章节块        有结构化摘要 → 按小节切分，保留小节名
    整段块        无结构化摘要 → 整段切分

**实测数据**：1264 篇文献 → 4956 个文本块（平均 3.9 块/篇）

**切块质量要求**：单块 300~700 字。过短（<100 字）检索时信息量不足；
过长（>1500 字）会稀释相关性，且引用时指向的片段不精确。

**关键踩坑（PDF 抽取）**

处理用户提供的 41 份 PDF 时发现一个灾难性缺陷：早期实现的
`merge_wrapped_lines` **反复扫描并合并行直到不再变化**。当某行结尾既不是
句末标点、也不是标题时，会与下一行合并；合并后的行**仍不满足**结束条件，
继续合并——**一路吞掉整篇文档**。

| 文件 | 旧方法 | 修正后 | 提升 |
|------|--------|--------|------|
| 直肠肿瘤三维可视化指导精准手术专家共识 | 178 汉字 | 10,550 | **59 倍** |
| 结直肠癌肝转移诊断和综合治疗指南（2025） | 1,149 汉字 | 16,349 | **14 倍** |

**而我的「防御措施」放大了危害**：`clean_draft.py` 里加的

    if len(para) > 4000:
        para = para[:4000] + "……（本段过长已截断）"

在合并失控产生万字符巨行时**直接删掉了内容**。

**修正方案**：改用 PDF 版面块（`page.get_text("blocks")`），
用 PDF 解析器已完成的版面分析，**块边界即段落边界**，不再猜标点。
并处理分栏：按 x 坐标把块分到左右栏，栏内按 y 排序。

## 6. 分类标注

**职责**：自动判定文献的围术期分期与证据等级。

**实现**：`app/etl/classifier.py`（191 行）。

**两个标注维度**

| 维度 | 取值 | 判定依据 |
|------|------|---------|
| 围术期分期 | preop / intraop / postop / general | 关键词计数 + 置信度 |
| 证据等级 | guideline / systematic / rct / cohort / review / case / other | 优先用 PubMed 出版类型，否则按标题与摘要推断 |

**为什么优先用出版类型**：PubMed 的 `publication_types` 字段由编目人员标注，
比从文本推断准确。只有当该字段缺失时才回退到文本推断。

**实测分布**（历史口径 120 篇；现行 109 篇，见《检索评测与复核报告》）

    证据等级：指南 60 / 综述 20 / 系统评价 15 / RCT 11 / 其他 9 / 队列 5

**局限与人工覆盖**：分类器按关键词匹配，对跨阶段内容会误判。
实测《中国结直肠癌筛查与早诊早治指南》被判为 `postop`（置信度 0.60），
而筛查指南应属 `general`。

**解决**：人工录入的文献可在元数据中声明分期与证据等级并覆盖分类器结果。
覆盖**仅对人工录入生效**（`phase_hint` 只由 manual_import 设置），
PubMed 文献继续走纯自动标注，保证既有评测结果可比。

## 7. 中文指南人工录入

**职责**：把用户提供的中文指南/共识全文导入知识库。

**实现**：`app/etl/manual_import.py`（239 行）、
`scripts/pdf_to_manual.py`、`scripts/extract_by_blocks.py`

**为什么必须人工录入**：PubMed 不提供中文正文（见第 4 节实测）。
中文语料只能靠人工整理。

**文件格式**：一份指南 = 一个 Markdown 文件。

    # 指南标题
    
    **作者**：编写组
    **期刊**：中华胃肠外科杂志
    **年份**：2025
    **证据等级**：guideline
    **分期**：general
    
    ## 章节名
    
    正文段落……

**为什么用 Markdown 而不是把内容写进代码**：
指南正文数千至数万字，章节结构需保留（章节即检索单元），
且医学文本需多人复核——代码文件不适合作为校对载体。

**约定**：文件名以下划线开头的是参考资料（模板、清单），不参与导入。

**导入命令**

    python -m app.etl.cli manual --dry-run   # 预览
    python -m app.etl.cli manual             # 导入

**可反复执行**：按标题归一化去重（忽略全角半角括号、空格、标点），
改完某一章重新导入会**更新**该文献而非新建重复记录。

**实测成果（这解决了项目最核心的限制）**

| 指标 | 整理前 | 现在 |
|------|--------|------|
| 含中文的文本块 | **10**（0.2%） | **1,314（76.5%）** |
| 「吻合口漏」原生命中 | 1 处 | **46 处** |
| 「新辅助」原生命中 | **0 处** | **154 处** |

**整理的 41 份 PDF**：入库 38 份，总汉字 378,336，平均 9,956 汉字/篇，
生成 1,533 个文本块。

**踩坑**

1. **UTF-8 BOM 导致整篇静默跳过**——文件首行 `# 标题` 带 BOM 后变成
   `\ufeff# 标题`，解析失败报「缺少一级标题」，整篇被跳过；
   而导入日志显示「更新 1 篇」（那是另一篇的统计），极具误导性。
   已改用 `utf-8-sig` 读取 + 解析层兜底剥离。

2. **CJK 正则误用 raw string**——`re.compile(r"[\u4e00-\u9fff]")` 中的
   `\u4e00` 不被解析为转义序列，正则实际在匹配字面串 `u4e00`~`u9fff`。
   难发现是因为 `_has_cjk("吻合口漏")` 恰好返回 True。

# 第三部分 检索层（在线）

## 8. 多路召回

**职责**：用三种互补方式召回候选文本块。

**实现**：`app/services/hybrid_search.py`（243 行）、
`app/repositories/search_repo.py`（181 行）

| 路径 | 机制 | 优势 | 实测贡献 |
|------|------|------|---------|
| 向量检索 | BGE-M3 稠密向量 + HNSW | 语义匹配，跨语言 | **主力** |
| 关键词检索 | 中文 bigram + GIN 索引 | 精确术语命中 | **贡献极低（见下）** |
| 图谱检索 | Neo4j 关系扩展 | 概念关联、多跳 | 见第 11 节 |

**中文关键词检索的实现难点**

PostgreSQL 的 pg_trgm 完全忽略非 ASCII 字符，对中文静默失效。
方案：把中文切成 bigram 词元（「吻合口漏」→ 吻合/合口/口漏），
用 `text[]` + GIN 倒排索引召回。

**但不过滤会导致长查询召回大量仅共享 1~2 个常见词元的无关文档**，
且这些文档在融合时会被当成「多路共识」提权。因此加了最小重叠比例过滤
（`min_keyword_overlap=0.3`）。

**实测：关键词检索对自然语言提问几乎无效**

| 评测集 | 仅关键词 R@5 | 相对仅向量 |
|--------|-------------|-----------|
| 中文 138 题 | **0.043** | −30.4 pp |
| 英文 136 题 | **0.081** | −36.8 pp |

**英文场景更严重**（R@1 仅 0.029），因为口语提问与学术文本的词汇体系不同：
用户问「这两个术式在并发症上有什么区别」，文献写的是
"robotic versus conventional laparoscopic surgery"。

## 9. RRF 融合

**职责**：把多路召回结果合并为单一排序。

**实现**：`app/services/fusion.py`

**为什么用倒数排名融合（RRF）**：它**只用名次不用分值**，
避免不同来源的分值无法归一化的问题（向量余弦相似度 0~1、
关键词命中数是整数、图谱路径分数是自定义的）。

**公式**：`score(d) = Σ weight_i / (k + rank_i(d))`，k=60

**权重配置**：`vector_weight=1.0`、`keyword_weight=0.3`、`graph_weight=0.6`

**实测：权重需要压低**

| 配置 | 中文 R@5 | 英文 R@1 |
|------|---------|---------|
| w=0.7 | 0.355 | **0.044** |
| w=0.3 | 0.355 | **0.073（+66%）** |

英文场景对噪声更敏感。

**踩坑**：RRF 曾直接修改输入列表，导致后续配置读到被污染的数据。
修复为 `dataclasses.replace` 生成新对象。

## 10. 交叉编码器重排

**职责**：对融合后的候选逐对精算相关性，重新排序。

**实现**：`app/services/model_registry.py` 加载 bge-reranker-v2-m3

**与向量检索的区别**：向量检索是**双塔**结构（查询与文档分别编码，
只算向量距离）；重排是**交叉编码器**（查询与文档拼接后一起输入模型），
精度更高但无法预计算，因此只对少量候选执行。

**实测：这是唯一显著有效的单项优化**

| 评测集 | R@5 提升 | MRR 提升 |
|--------|---------|---------|
| 中文 | **+10.1 pp** | **+14.1 pp** |
| 英文 | **+18.4 pp** | **+17.2 pp** |

覆盖两种语言、两种提问风格——**四轮评测中最稳定的结论**。

**代价**：延迟从 0.6 秒升至 3.2 秒（重排候选上限 80 条时约 105 对/秒）。

## 11. 知识图谱检索

**职责**：沿实体关系扩展，补充文本检索难以覆盖的关联性查询。

**实现**：`app/services/graph_client.py`（231 行）、`extraction.py`（301 行）、
`graph_ingest.py`（201 行）、`graph_search.py`（363 行）

**图谱规模**：1423 实体节点 / 1380 关系，8 类实体 / 10 类关系

**构建流程**：从文本块抽取实体与关系 → 写入 Neo4j。
**注意**：必须先写实体再写关系，否则关系会被静默丢弃
（实测 1831 条尝试写入，仅 1380 条成功）。

**实体索引磁盘缓存**：冷启动需 61.8 秒编码实体名，
加入磁盘缓存（`data/eval/graph_entity_index.json`）后降至 1.02 秒（62 倍）。

**实测：对中文有益、对英文有害**

| 场景 | 融合 w=0.7 时 R@5 |
|------|------------------|
| 中文 | 0.355（与向量持平） |
| **英文** | **0.324（比仅向量 0.449 低 12.5 pp）** |

原因是**实体用中文抽取**，英文查询需跨语言匹配中文实体名，种子质量下降。

**APOC 不可用**：Neo4j 社区版默认不含 APOC 插件，全部图操作用纯 Cypher 实现
（包括用 `reduce` 做去重）。

**一个差点写进论文的错结论**：首次图谱消融实验显示贡献为 **0.0**。
核实后发现那次评测使用的 `SearchRequest.use_graph` 默认值仍为 `False`，
所以图谱路径没有实际执行。修复后默认值为 `True`，后续评测确认了图谱召回路径确实执行。

**教训：任何消融实验都必须先确认被消融的组件确实执行了。**

# 第四部分 生成层

## 12. 提示词构造

**职责**：把检索到的证据组装为约束大语言模型行为的提示词。

**实现**：`app/services/prompts.py`（170 行）

**结构**：系统角色 + 回答要求 + 证据片段（带编号）+ 用户问题

**要求模型遵守的规则**：只用给定证据作答、每处结论标注来源编号、
不写出证据中没有的数值、证据不足时明确说明。

**实测：提示词工程无法解决忠实度问题**

用**同一批 40 道题**做 A/B 对照：

| 指标 | 加固前 | 加固后 |
|------|--------|--------|
| 忠实度 | 0.733 | 0.721 |
| **数值编造占比** | 22% | **26%（不降反升）** |
| 归因错误 | 1 条 | 0 条 |

**明确禁止后数值编造反而上升。** 个别编造案例在后一次运行中逐字重现。

**结论**：医学 RAG 的忠实度问题必须靠**结构化校验**而非提示词解决。

## 13. 大语言模型调用

**职责**：调用 DeepSeek API 生成答案，支持流式与非流式。

**实现**：`app/services/llm_client.py`（242 行）

**模型选择**

| 模型 | 首字延迟 | 说明 |
|------|---------|------|
| deepseek-flash | 2.0 秒 | **选用** |
| deepseek-v4-pro | 13.6 秒 | 过慢 |

**注意**：`deepseek-chat` 会静默回退到 flash，需显式指定模型名。

**踩坑：推理模型返回空答案**

DeepSeek 推理模型的思考过程计入 `max_tokens`。实测：

| max_tokens | 空答案比例 |
|-----------|-----------|
| 512 | **100%** |
| 1024 | 25% |
| 8192 | 0% |

修复：捕获 `reasoning_content`，并在 `max_tokens` 不足时重试。

## 14. 引用解析与校验

**职责**：解析答案中的 `[n]` 引用标记，剔除模型编造的无效编号。

**实现**：`app/services/citation.py`（288 行）

**两件事**

1. **引用解析**：把答案中的 `[n]` 映射到具体的证据片段
2. **有效性校验**：模型中引用了实际不存在的编号时记录为幻觉信号

**实测**：40 条答案中**无效引用率为 0.000**——没有任何一条编造了不存在的文献编号。

**前端渲染的踩坑**：Markdown 渲染会吞掉 `<sup>` 标签。
修复方案是用哨兵标记：先生成 `@@CITE{n}@@`，渲染后再替换为
`<sup class="cite">`。实测 10/10 正确恢复。

## 15. 数值主张核验

**职责**：逐个核验答案中的数值能否在证据中找到依据。

**实现**：`app/services/rag_service.py` 的核验步骤

**方法**：用正则提取答案中的百分比、比值、样本量、时长，
逐个在检索到的证据全文中比对，找不到的标记为「无据数值」。

**为什么需要这一层**：提示词加固实验证明模型会编造精确细节
（如「中转率 7.1% vs 3.4%」这类看起来专业的数值），
**临床医师看到具体百分比会本能信任，这类错误危害最大**。

**实测效果**：175 处数值中捕获 8 处无据数值（错误率 4.6%），
**而 LLM 裁判并没有明确指出这些**。

# 第五部分 场景应用

## 16. 单轮问答

**职责**：从提问到带引用答案的完整闭环。

**实现**：`app/services/rag_service.py`（267 行）、`app/api/v1/qa.py`

**六步流程**

    ① 检索      多路召回 + RRF 融合 + 重排
    ② 组装证据  筛选相关性达标的片段
    ③ 构造提示词
    ④ 调用 LLM
    ⑤ 引用解析  剔除无效编号
    ⑥ 数值核验  标记无据数值

**关键的防幻觉设计**：若检索最高分低于阈值（`MIN_EVIDENCE_SCORE = 0.05`），
**不调用大语言模型**，直接返回「证据不足」提示。
这是从源头杜绝无依据作答。

**两种接口**

| 接口 | 特点 |
|------|------|
| `POST /api/qa` | 非流式，返回完整答案与 token 用量 |
| `POST /api/qa/stream` | SSE 流式，逐字返回（前端体验好） |

**流式接口的踩坑**：Vite 开发代理会丢弃约 34 个增量（607 vs 573）。
修复：以 `done.answer` 为权威答案，并提供非流式修复接口。

## 17. 多轮对话与查询改写

**职责**：识别追问中的指代与省略，还原为独立可检索的查询。

**实现**：`app/services/conversation.py`（334 行）

**为什么必须做**：检索依赖语义完整的独立查询串。
医师的追问「**它的**发生率是多少？」如果直接送去检索，
查询中没有任何医学实体，**检索会完全失效**。

**三个功能**

1. **查询改写**：结合对话历史把追问还原为完整查询
2. **意图识别**：判定问题类型（概念定义 / 诊断评估 / 处理治疗 / 证据预后 / 比较选择）
3. **会话管理**：`ConversationStore`，200 个会话，LRU 淘汰，保留 10 轮

**实测改写效果**

| 原始追问 | 改写结果 |
|---------|---------|
| 它的发生率是多少？ | 结直肠癌术后吻合口漏的发生率是多少 |
| 那荧光造影有什么证据支持？ | 术中吲哚菁绿（ICG）荧光血管造影评估肠道吻合口血供有哪些证据支持 |

**是否改写的启发式**：追问含指代词（它/这个/那）或长度过短时触发改写，
避免对已完整的提问做无谓的改写。

## 18. 影像辅助解读

**职责**：接收术中影像，输出有文献依据的辅助解读。

**实现**：`app/services/image_analysis.py`（230 行）、
`vision_client.py`（195 行）、`app/api/v1/images.py`（280 行）

**三阶段流水线**

    ① VLM 客观描述    多模态模型输出影像所见
    ② 由描述构造检索查询
    ③ 结合文献证据综合  给出辅助解读并标注来源

**关键的合规定位**：**模型仅负责客观描述，结论性表述必须由文献证据支撑**。
影像解读定位为辅助而非诊断。

**实测耗时**

| 场景 | 耗时 |
|------|------|
| 冷启动 | 113.0 秒（VLM 23.3 + 检索 76.6 + 综合 12.8） |
| 热态 + 缓存 | **14.3 秒** |

**踩坑**

1. **GLM-4V 的 max_tokens 限制**：传 400 报错
   `max_tokens参数非法：限制数值范围[1,1024]`。
   修复：按模型设上限并自动钳制（`MODEL_MAX_TOKENS`）。

2. **检索查询被推测词污染**：VLM 描述含「可能」「清晰度」这类词，
   直接送去检索会命中无关文档。修复：`_NOISE_PATTERNS` 剥离推测与质量词，
   查询长度从 184 字降至 111 字。

# 第六部分 系统管理与评测

## 19. 用户权限

**职责**：账号管理、认证、基于角色的权限控制。

**实现**：`app/core/security.py`（163 行）、`permissions.py`（150 行）、
`app/api/v1/auth.py`（388 行）、`app/api/deps.py`（174 行）、
`app/middleware/auth.py`（65 行）

**角色设计**

| 角色 | 权限数 | 能力 |
|------|--------|------|
| 管理员 | 21 | 全部 |
| 医师 | 9 | 问答、影像、反馈、查看配置；**不能改语料与用户** |

**为什么不采用自由权限位**：本系统只面向院内两类使用者，
自由权限位会增加配置复杂度与误配风险。角色到权限的映射集中在
`permissions.py`，新增权限只需改该文件。

**认证方案**：JWT（HS256），有效期 8 小时。

**为什么不主动吊销单令牌**：JWT 无状态，代价是无法吊销。
补偿措施：每次请求都校验用户当前状态（`is_active` / 锁定），
用户被停用后其未过期令牌立即失效。

**密码哈希**：直接调用 bcrypt（不用 passlib——它与 bcrypt 4.1+ 有兼容问题）。

**踩坑：bcrypt 5.0 的行为变更**

bcrypt 5.0 **不再自动截断超 72 字节的口令，而是抛 ValueError**。
旧版会静默截断，因此升级后才暴露。已在哈希与校验前统一按 72 字节截断
（按 UTF-8 边界回退，不破坏多字节字符）。

**踩坑：登录接口被自己的认证拦死**

启用「默认拒绝」策略后，`/api/auth/login` 也被中间件拦截返回 401——
**没有人能登录**。已加入公开路径白名单。

**默认拒绝的落地方式**：中间件在路由匹配前判断
`is_public_path(method, path)`，未声明的路径一律需要认证。
这样新增接口时忘记声明权限，**出错方向是安全的**（会要求登录，而非无保护暴露）。

## 20. 知识库维护

**职责**：文献审核、更新、版本管理、质量评估。

**实现**：`app/api/v1/knowledge.py`（519 行）、`kb_repo.py`（447 行）、
`services/kb_jobs.py`（399 行）

**四项功能**

| 功能 | 实现 |
|------|------|
| 审核 | 逐篇/批量审核，驳回自动下架；八维筛选 |
| 更新 | 界面触发 PubMed 采集与向量化，后台执行 |
| 版本管理 | 每次更新记录检索式、参数、结果计数、耗时、操作人 |
| 质量评估 | 六维报告 + 自动生成维护建议 |

**后台任务机制（kb_jobs.py）**

采集 + 向量化是数十分钟级的操作，放 HTTP 请求内必然超时。改为：

    提交 → 立即返回 202 与 job_id
    后台线程执行，每完成一个检索式更新进度
    前端每 2 秒轮询进度
    完成后刷新列表

**两级状态存储**：数据库存最终结果（持久、可追溯），
内存字典存实时进度（每秒变化，写库无必要）。

**并发控制用「拒绝」而非「排队」**：向量化占 GPU，第二个请求直接返回 409
——排队会让管理员误以为任务已开始。

**质量评估的六个维度**：规模 / 时效性 / 证据结构 / 分期覆盖 / 语种结构 / 审核进度，
外加**可执行的异常清单**（哪些文献缺摘要、缺标识符、未向量化）。

**权限设计**：所有写操作仅限管理员。审核决定文献是否进入检索池，
会直接影响全系统所有用户的答题依据，属**发布决策**而非个人判断。

**「下架」与「彻底删除」的区分**：下架是主操作（可恢复，历史引用仍有效），
彻底删除藏在详情对话框内并要求二次确认。依据是**误删代价不对称**。

## 21. 问答质量监控

**职责**：记录问答指标、收集人工反馈、支持持续优化。

**实现**：`app/services/qa_logging.py`（75 行）、`qa_log_repo.py`（337 行）

**记录的是指标而非全文**：答案正文可能上千字，逐条存储会让日志表迅速膨胀。
实际需要的是问题、引用数、无效引用数、耗时、幻觉信号等指标，
以及用于回溯的会话与文档标识。

**反馈设计**：采用 1~5 分制而非简单好评/差评——
二值反馈无法区分「略有不足」与「完全错误」，
而这两者对优化方向的指示完全不同（前者调检索，后者要查幻觉）。

**问题类型标签**：准确 / 信息不完整 / 答非所问 / 存在编造 / 引用错误 / 其他，
便于聚合统计与定向优化。

**「持续优化」的落地方式**：本模块不实现自动训练（超出本课题范围），
而是提供可操作的闭环：反馈按类型聚合 → 定位问题类别 → 定向改进语料或检索策略。

## 22. 系统配置

**职责**：在线管理模型参数、检索策略与运行配置。

**实现**：`app/repositories/config_repo.py`（350 行）

**15 项可配置参数**，分三类：检索（9）/ 模型（2）/ 系统（4）

**白名单机制**：`DEFAULT_CONFIGS` 既是默认值来源，也是**允许修改的参数白名单**。
接口只接受白名单内的 key，避免管理员注入任意参数。

**取值校验**：数值型参数有 `min_value` / `max_value`。
配置直接作用于检索与生成链路，越界值（如权重设为 100）会让系统表现完全失控。

**生效时机需如实区分**：检索权重在每次检索时读取（立即生效），
与已加载模型绑定的参数需重启。界面明确标注，否则管理员会以为调整已生效而实际没有。

## 23. 评测框架

**职责**：量化检索质量与生成质量。

**实现**：`app/eval/`：`dataset.py`、`generator.py`（398 行）、
`runner.py`（422 行）、`metrics_retrieval.py`、`cli.py`（246 行）

**评测集构建方式**：从知识库文本块**反向生成问题**，该文本块即标准答案来源。
好处是检索指标完全客观可复现。

**关键的防泄漏设计**：若直接让模型「根据这段文字提问」，
它会逐字摘抄原文术语，导致关键词检索虚高、评测失去意义。
因此提示词**强制要求换用同义表达和口语化提问**。

**指标口径**：Recall@K / MRR / NDCG@K，**单答案标注、gold chunk 精确匹配**。

**实测结果（历史口径 120 篇语料；现行 109 篇 / 3,772 块）**

| 配置 | 中文 R@5 | 英文 R@5 |
|------|---------|---------|
| 仅向量 | 0.348 | 0.449 |
| 仅关键词 | 0.043 | 0.081 |
| 融合 + 重排 | **0.449** | **0.632** |

**消融实验的四条结论**

1. 重排是唯一显著有效的单项优化（中文 +10.1 pp / 英文 +18.4 pp）
2. 关键词检索对自然语言提问几乎无效，且拖累融合
3. 知识图谱对中文有益、对英文有害（跨语言实体匹配损失）
4. 证据等级加权损害召回（−5.1 pp），但设计目标不是提升召回

**评测集重建的必要性**：语料从 444 篇换成 120 篇后，
旧评测集**92% 的金标准已不在语料中**，沿用会让指标失去意义。
因此用同一流程、同一随机种子重建（中文 138 题 / 英文 136 题）。

**局限**：单答案标注——一个临床问题的答案常分布在多个文本块，
因此本指标是**召回率的下界**。
