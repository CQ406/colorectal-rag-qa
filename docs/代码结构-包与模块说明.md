# 代码结构：每个包负责什么

> 数据来源：2026-11-16 实测统计（文件数与行数取自当前代码）。
> 后端 `backend/app` 共 8 个包 + 2 个根模块；前端 `frontend/src` 共 7 个包 + 3 个根文件。

---

## 一、整体分层

```
            ┌──────────────────────────────────────────────┐
   请求 →   │ api/            接口层：路由、参数校验、SSE   │
            ├──────────────────────────────────────────────┤
            │ services/       业务层：检索、生成、图谱、影像 │
            ├──────────────────────────────────────────────┤
            │ repositories/   数据访问层：只拼 SQL，不做业务 │
            ├──────────────────────────────────────────────┤
            │ models/         表结构（SQLAlchemy ORM）      │
            └──────────────────────────────────────────────┘
   离线：   etl/  文档解析 → 切块 → 向量化 → 入库
   评测：   eval/ 评测集、指标、消融跑批
   横切：   core/ 配置/权限/安全/日志/常量；db/ 连接池；middleware/ 认证中间件
```

**依赖方向是单向的**：`api → services → repositories → models`。
反过来不允许 —— 例如 `services` 不会 import `api`，`repositories` 不 import `services`。
（唯一例外是少数仓储为了复用分页工具而 import `schemas`，属于数据传输对象的共享。）


## 五、几处刻意的结构选择

| 选择 | 原因 |
|---|---|
| `repositories` 不写业务 | 业务规则变化频繁，SQL 相对稳定；混在一起会导致改规则时被迫改 SQL |
| `schemas` 集中一个文件 | 接口契约要一眼对齐前后端；分散后容易漏改 |
| `services` 拆 25 个文件 | 检索、生成、图谱、影像、会话各自独立，避免出现"一个 3000 行的 service" |
| `etl` 与 `services` 分开 | 离线入库与在线问答的生命周期、失败代价完全不同 |
| `core/permissions.py` 集中权限 | 权限分散在各路由会出现"某接口忘了加校验"（已修复过 `/api/models` 就是这种情况） |
