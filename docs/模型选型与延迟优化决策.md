# 模型选型与延迟优化决策记录

> 实测日期：2026-10-07
> 测量脚本：`backend/scripts/benchmark_models.py`、`backend/scripts/compare_models.py`
> 目的：为「单段生成 vs 两段式生成（flash 草稿 + v4-pro 精修）」提供选型依据

---

## 一、背景：为什么考虑两段式

阶段四首次跑通时，问答的端到端耗时为 15~32 秒，流式首字延迟 13.4 秒。
答辩演示场景下这个延迟体验较差，因此提出**两段式生成**方案：

1. 第一段用 `deepseek-flash`（预期更快）产出草稿，让用户先看到内容
2. 第二段用 `deepseek-v4-pro` 精修草稿，保证质量

**该方案的成立前提**：第一段必须显著快于第二段。

---

## 二、测量方法的修正

### 问题：单次测量结果自相矛盾

首次对比测量得到：

| 配置 | 首字延迟 | 总耗时 |
|------|---------|--------|
| flash@512 | 无输出 | 3.3s |
| flash@2048 | 7.25s | 7.85s |
| flash@4096 | 1.92s | 2.4s |
| v4-pro@4096 | 3.83s | 4.54s |

**4096 额度反而比 2048 快 3 倍**，物理上不可能。

同时该次测得 v4-pro 总耗时 4.54s，而阶段四首次验证测得 15~32s，
同一模型同一类任务的两次测量相差 3~7 倍。

**结论：API 侧存在显著波动，单次测量不可用于架构决策。**

### 修正后的方法

`benchmark_models.py` 采用：

1. **多次采样**（默认 4 次），报告 min / median / max 而非单点
2. **交替请求**各配置，避免「先跑的配置遇到冷启动」造成系统性偏差
3. **流式测量**，区分「首字延迟（TTFT）」与「总耗时」
4. 额外记录**推理内容占比**，定位延迟的真实来源

## 三、实测结果（各配置 4 次采样）

| 配置 | 总耗时 min/med/max | 首字延迟 med | 推理占比 | 空答案次数 |
|------|-------------------|-------------|---------|-----------|
| flash@1024 | 3.25 / **3.85** / 5.40 | 3.26s | 85% | **1/4** ❌ |
| flash@2048 | 2.24 / **3.20** / 7.60 | 2.65s | 68% | 0 |
| flash@4096 | 2.73 / 5.12 / 5.70 | 4.69s | 77% | 0 |
| v4-pro@2048 | 2.74 / 4.13 / 4.74 | 3.60s | 74% | 0 |
| **v4-pro@4096** | 3.42 / **4.59** / 7.19 | **4.03s** | 82% | 0 |

## 四、三个关键事实

### 事实 1：v4-pro 单独就足够快，两段式反而更慢

- v4-pro@4096 中位总耗时：**4.59 秒**
- flash@4096 中位总耗时：5.12 秒（**比 v4-pro 还慢**）
- 两段式预估总耗时：**9.71 秒**（flash + v4-pro 串行）

**两段式比单段慢 5.1 秒。**

更关键的是：flash 并不比 v4-pro 快。原方案假设「flash 快、v4-pro 好」，
但实测两者速度相当（3.20s vs 4.59s，且 flash 的方差更大）。
因此两段式不是「用速度换质量」，而是**把同等成本付两遍**。

### 事实 2：延迟根源是推理开销，换模型无法规避

推理内容（`reasoning_content`）占 completion token 的 **68~85%**：

| 配置 | 推理占比 |
|------|---------|
| flash@1024 | 85% |
| flash@2048 | 68% |
| flash@4096 | 77% |
| v4-pro@4096 | 82% |

**两个模型都是推理模型**，都要先完成思考再输出正式答案。
所以「换一个更快的模型」不能解决延迟——延迟不是模型档位造成的，
而是这个 API 的推理机制决定的。

### 事实 3：flash 会不可靠地返回空答案

flash@1024 的 4 次采样中**有 1 次返回空答案**（`finish_reason='length'`，
100% token 用于推理，`content` 为空）。

原因：推理内容计入 `max_tokens`，额度不足时推理阶段就耗尽配额。
`flash@512` 更是 100% 空答案。

**用 flash 做草稿段会随机失败**，答辩现场出现空答案的风险不可接受。

### 附：首次 15~32 秒的成因

阶段四首次验证的 15~32 秒，经分析是以下因素叠加：

1. **提示词更长**：阶段四送入 5 条证据（约 1200~1500 token），
   本基准测试只送 3 条（约 364 token），输入更长导致推理更久
2. **冷启动**：首次调用伴随模型侧预热
3. **API 波动**：即便同配置，实测 min/max 可相差 2~3 倍

因此**不能简单认为「问答需要 30 秒」**，也不能认为「一定只要 4.6 秒」。
论文中报告性能时应给出分位数而非单点值。

## 五、最终决策

### 采用单段 v4-pro，不实施两段式

| 决策项 | 取值 | 依据 |
|--------|------|------|
| 生成模型 | `deepseek-v4-pro` | 中位总耗时 4.59s，快于 flash 且质量更稳 |
| `max_tokens` | 4096 | 实测 2048 亦可，但 4096 给推理留足余量，避免空答案 |
| 两段式 | **不采用** | 预估 9.71s，比单段慢 5.1s |
| 空答案防护 | 客户端显式抛错 | 推理模型的行为特性，必须防 |

### 延迟优化的正确方向

既然瓶颈是推理开销，优化应针对「让用户感知不到等待」，而非「减少推理」：

1. **流式输出 + 思考指示器**（前端实现）
   首字延迟约 4 秒，期间前端应显示「正在检索证据…」「正在推理…」等状态，
   而不是空白等待。这是体感优化的主要手段。

2. **模型预热**
   答辩演示前调用 `POST /api/models/load` 预加载检索模型，
   可消除首次调用的 10~15 秒模型加载开销（这部分与 LLM 无关）。

3. **答案缓存**
   高频问题的答案可缓存至 Redis，重复提问直接返回。

4. **若必须进一步压缩延迟**（需重新评估，非当前目标）：
   - 减少送入 LLM 的证据条数（`top_k` 从 5 降到 3）→ 输入变短，推理更快
   - 但会降低答案完整性，需用评测集验证权衡

### 论文中的表述建议

> 本系统生成阶段采用 DeepSeek-V4-Pro 推理模型，实测端到端中位耗时
> 4.59 秒（min 3.42s / max 7.19s，n=4），其中推理内容占生成 token 的 82%。
> 我们曾评估「小模型草稿 + 大模型精修」的两段式方案，但实测显示
> 两模型延迟相当（3.20s vs 4.59s），两段式总耗时 9.71 秒反而劣于单段，
> 故未采用。这表明在推理模型场景下，延迟瓶颈来自推理机制本身，
> 而非模型规模，两段式加速策略不适用。
