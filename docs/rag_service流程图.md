# `rag_service.py` 内部流程图

> 配套代码：`backend/app/services/rag_service.py`
> 这是整个系统的枢纽，两个入口函数：`answer()`（非流式）与 `answer_stream()`（流式）

---

## 一、`answer()` 完整流程

```
┌─────────────────────────────────────────────────────────────┐
│  入口：answer(db, req)                                      │
│  入参：QaRequest(question, top_k, phase, recall_mode, ...)  │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ ① 检索  hybrid_search.search(db, search_req)                │
│                                                              │
│    内部四路召回 ──→ RRF 融合 ──→ 交叉编码器重排             │
│      · 向量（BGE-M3 语义）                                   │
│      · 关键词（中文 bigram 倒排）                            │
│      · 图谱（Neo4j 实体 + 多跳）                             │
│                                                              │
│    产出：SearchResponse(results=[RetrievedChunk, ...])       │
└─────────────────────────────────────────────────────────────┘
                            ↓
              ┌─────────────┴─────────────┐
              ↓                           ↓
    ┌───────────────────┐      ┌──────────────────────────┐
    │ 结果为空？         │      │ 证据强度不足？            │
    │                   │      │ top_score < min_evidence │
    │                   │      │ _score（默认 0.05）       │
    └───────────────────┘      └──────────────────────────┘
              ↓ 是                        ↓ 是
    ┌──────────────────────────────────────────────────────┐
    │ _no_evidence_answer()  ← 防幻觉第 1 层               │
    │ **不调用 LLM**，直接返回"未找到足够证据"              │
    │                                                       │
    │ 为什么这样做：无依据时调用 LLM，模型必然依赖自身知识  │
    │ 作答，必然产生无法溯源的幻觉。宁可不答。              │
    └──────────────────────────────────────────────────────┘
              ↓ 否（继续）
┌─────────────────────────────────────────────────────────────┐
│ ② 组装证据  evidences_from_search()                          │
│                                                              │
│    把 RetrievedChunk 转成带**编号**的证据字典：              │
│      {index: 1, doc_title, journal, year, page_start,        │
│       evidence_level, phase, content}                        │
│                                                              │
│    编号 index 是引用体系的锚点 —— LLM 输出 [1] 就对应这里     │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ ③ 构造提示词  build_qa_prompt(question, evidences, phase)   │
│                                                              │
│    渲染成文本：                                              │
│      [证据 1] 标题（期刊, 2023）第 850 页 | 证据等级：指南   │
│      正文内容...                                             │
│                                                              │
│  提示词含防幻觉约束（防幻觉第 2 层）——见 prompts.py          │
│    · 只依据证据作答，不用自身知识                             │
│    · 数值必须逐字来自证据（**实测此约束无效**，见下）        │
│    · 不得把 A 文献结论归因给 B 文献                          │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ ④ LLM 生成  LLMClient().chat([system, user])                │
│                                                              │
│    客户端内置保护（llm_client.py）：                         │
│      · reasoning_content 捕获（推理模型的思考过程）          │
│      · **空内容检测 + 自动重试**                             │
│        （推理模型 max_tokens 不足时返回空串）                │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ ⑤ 引用解析  build_citations(content, evidences)             │
│                                                              │
│    用正则扫出答案中的 [n] 标记：                             │
│      · 存在的编号 → citations 列表（含页码、片段）           │
│      · **不存在的编号 → invalid_citations（防幻觉第 3 层）** │
│                                                              │
│    例：LLM 写了 [7] 但只给了 5 条证据 → 7 进入 invalid 列表  │
│    这是量化"幻觉引用率"的依据，阶段十实测该值为 0.000        │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ ⑥ 数值核验  verify_numeric_claims(content, evidence_texts)  │
│                                          ← 防幻觉第 4 层     │
│                                                              │
│    正则提取答案中的数值主张：                                │
│      百分比 / 比值(OR,HR) / 样本量(n=,例) / 时长            │
│    逐个在证据全文里查找（去千分位、百分比与小数互转）        │
│      · 找不到 → unsupported_numbers                          │
│                                                              │
│    **为什么必须有这一层**：                                  │
│    阶段十实测 —— 在提示词里明确禁止写证据外的数字后重测，    │
│    数值编造占比 **22% → 26%（不降反升）**，                   │
│    个别案例（PROSPECT/NORAD、30% pCR）**逐字重现**。          │
│    结论：提示词无法解决，必须结构化校验。                    │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  出口：QaAnswer(question, answer, citations,                 │
│                 invalid_citations, unsupported_numbers,      │
│                 numeric_warning, evidences, timings, usage)  │
└─────────────────────────────────────────────────────────────┘
```

## 二、四层防幻觉设计（论文核心内容）

| 层 | 位置 | 机制 | 实测效果 |
|----|------|------|---------|
| **①** | `answer()` 步骤 ① | 检索为空或分数低于门槛 → **不调用 LLM** | 从源头杜绝无据作答 |
| **②** | `prompts.py` | 提示词硬约束（只用证据、禁编数字、禁错误归因） | **数值编造无效**（22%→26%）；归因错误有效（1→0 条） |
| **③** | `citation.build_citations` | 引用编号校验，不存在则剔除并记录 | 幻觉引用率 **0.000** |
| **④** | `citation.verify_numeric_claims` | 数值主张与证据比对 | 数值错误率 **4.6%**（8/175 处） |

**这一层设计的关键洞察**：第 ② 层（提示词）看起来最"高级"，但**实测最不管用**。
真正有效的是 ①③④ —— 都是**结构化、不依赖模型配合**的机制。

> 写论文时这是一个好的论点：**医学 RAG 的忠实度问题不能靠提示词工程解决，
> 必须靠可验证的结构性约束。** 数据见 `data/paper/experiment_results.md`。

## 三、`answer_stream()` 与 `answer()` 的差异

| 方面 | `answer()` | `answer_stream()` |
|------|-----------|------------------|
| 输出 | 一次性返回完整 `QaAnswer` | 生成器，逐条 yield 事件字典 |
| 传输 | 普通 JSON | SSE（`data: {json}\n\n`） |
| 事件序列 | — | `retrieval` → `delta`×N → `done` |
| 引用先行 | 生成后才解析 | **`retrieval` 事件先送证据**，前端可立即渲染引用面板 |
| 用途 | 评测、脚本、单次查询 | 前端交互（逐字显示） |

**为什么引用要先送**：首字延迟 3.6~5 秒，如果等答案生成完才给引用，
引用面板会空白 3 秒以上。先送 `retrieval` 事件让面板立刻有内容。

**注意**：流式路径的数值核验在 `done` 事件前执行，
但**前端仍需处理 Vite 代理丢事件的问题**（见 `stores/chat.ts` 的自动补偿）。

## 四、读代码时的三个关注点

**1. `timings` 字典贯穿始终**

每一步都记录耗时（`retrieval_ms` / `generation_ms` / `total_ms`）。
这是性能分析的依据，也是论文里延迟数据的来源。

**2. 异常处理的边界**

```python
except LLMError as exc:
    logger.error("LLM 生成失败: %s", exc)
    raise          # ← 向上抛，由 API 层转成 HTTP 503
```

服务层不吞异常，API 层负责转 HTTP 状态码。职责分离。

**3. `_no_evidence_answer()` 也会返回 `QaAnswer`**

它不是一个错误，而是**一种正常的回答结果**（`has_evidence=False`）。
前端据此显示不同的 UI（警告样式而非错误样式）。
