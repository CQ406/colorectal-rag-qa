# 启动与备份恢复手册

适用环境：Windows、PowerShell、Docker Desktop、Python 3.12、Node.js。配置 `.env` 单独保管，备份不包含密钥和模型权重。默认只监听本机回环地址。

## 安装与启动

在项目根目录创建环境并安装依赖。`constraints-20261108.txt` 是本机已安装依赖闭包的版本约束，未在全新机器上安装验证；CUDA 运行库、显卡驱动和本地模型目录仍需配齐。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt -c backend/constraints-20261108.txt
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-ml.txt -c backend/constraints-20261108.txt --extra-index-url https://download.pytorch.org/whl/cu128
cd frontend
npm ci --no-audit --no-fund
cd ..
docker compose up -d
```

复制 `.env.example` 到 `.env` 并填写数据库、模型目录、登录口令和 API 配置；已有 `.env` 不覆盖。首次初始化在 `backend` 目录执行：

```powershell
python -m scripts.init_db
python -m scripts.sync_schema
python -m scripts.sync_schema --dry-run
```

`--dry-run` 检出缺表、列或索引时返回非零；该检查只覆盖增量结构差异，不替代正式迁移历史及约束变更检查。同步不会删表、删列或清空记录。

在项目根目录启动：

```powershell
.\start-all.ps1 -SkipWarmup
# 已有后端需要更新时，明确指定重启；会核验进程身份：
.\start-all.ps1 -PythonPath 'D:\deep seek test\rag-venv\Scripts\python.exe' -RestartBackend -SkipWarmup
```

Python 查找顺序为 `-PythonPath` / `RAG_PYTHON` 环境变量 → `launcher.config.json` 的 `python` 字段 → 项目内 `.venv` / `venv` / `backend\.venv` / `backend\venv` → PATH 中的 `python`。
**每个候选都会用 `import fastapi, torch` 实际验证依赖**，第一个通过的被采用；全部失败时脚本会打印每个候选的路径与来源，并给出三种修复方式。

>
> ```json
> { "python": "D:\\deep seek test\\rag-venv\\Scripts\\python.exe" }
> ```
>
> 排查时可只检查不启动：`start.bat -CheckOnly`（参数会透传给 `start-all.ps1`）。需要预热时在当前终端设置 `RAG_ADMIN_TOKEN` 为有效管理员令牌，再去掉 `-SkipWarmup`；脚本不会把令牌写入日志。未预热时首次检索加载模型。

前端 `http://127.0.0.1:5173`，API `http://127.0.0.1:8000`。Vite 开发代理的后端可用 `VITE_API_TARGET` 配置。日志在 `logs/`。这些是本地开发启动方式；对外提供服务前仍需反向代理、HTTPS 和正式进程管理。

## 备份与隔离恢复演练

从 `backend` 目录运行；Python 使用项目环境：

```powershell
python -m scripts.backup_restore backup
python -m scripts.backup_restore backup-and-rehearse --with-graph
# 再次验证既有备份：
python -m scripts.backup_restore rehearse --backup 'D:\AI\RAG_project\data\backups\<备份目录>' --with-graph
```

每次创建独立目录，包含 PostgreSQL custom-format dump、Neo4j 节点和关系逻辑快照、本地影像与原始资料、病例来源 XML 和评测记录。`manifest.json` 记录每个文件的大小及 SHA256，`restore-report.json` 记录实际恢复证据。

第二轮已将 `data/document_sources/` 原文件快照、`data/reviews/` 复核与标注材料纳入备份；新增的 `kb_chunk_revision` 表随 PostgreSQL dump 保存。最新演练为 `data/backups/20261105T041240Z_8324ac/restore-report.json`：12 表、149 个资料文件、1556 节点/1500 关系及属性恢复一致，临时资源已清理。首次快照记录保留如下。

2026-11-05（本地时间）完成的最终数据快照演练：`data/backups/20261104T162532Z_b869ed/restore-report.json`，11 张表行数一致、146 个资料文件摘要一致、1556 节点/1500 关系及其属性一致。临时数据库和容器均已清理；目录名使用 UTC，故日期部分显示为 20261104。该备份记录采样时的数据，后续数据更新后应重新备份。

恢复演练先校验文件摘要，在 `rag_restore_<随机值>` 新库恢复，核对所有表行数；复制资料并逐个校验摘要。图谱在无生产数据卷、使用随机回环端口的独立临时容器恢复，核对节点、关系及属性。验证完只删除本次创建且身份核验通过的库和容器，恢复文件留在 `data/restore-rehearsal/`。正式库及运行中的图谱不作为恢复目标。

PostgreSQL dump 自身事务一致。文件和图谱快照在不同时间读取，生产备份应暂停写入以取得协调快照；本次演练期间未进行业务数据写入。Redis 为可重建缓存，未备份；会话正文已存在 PostgreSQL 中。

实际故障恢复应先保留现场，在新数据库和独立 Neo4j 实例中使用已验证备份恢复，核对后再修改应用配置指向恢复实例。不要将演练命令改成覆盖现有生产数据库。密钥、模型权重、数据库角色及外部存储配置需要另外恢复；当前库文献 `file_path` 均为空，内容已保存在数据库，资料副本保留在 `workspace/data/manual/`。未来引入绝对文件路径时应补充迁移映射。

## 验证与排查

```powershell
# 项目根目录
python -m pytest backend/tests -q
cd frontend
npm run build
$env:RAG_PYTHON='D:\deep seek test\rag-venv\Scripts\python.exe'
npm run test:e2e
```

浏览器验收默认使用已安装的 Edge，无头运行。测试仅创建 `rag_e2e_<随机值>` 数据库和 `data/e2e/` 文件，结束后清理测试数据库。若异常退出，可在确认测试已停止后运行 `python -m scripts.cleanup_e2e`；脚本校验专用前缀，拒绝删除正式库。

健康接口能访问但检索失败时，先检查模型目录和数据库结构；401 表示身份或令牌问题，不能当作模型预热成功。图谱节点数量不代表可检索来源有效，须核对来源文本块是否仍在上架语料中。

应用图谱写入通过 `GraphClient` 发布 `data/eval/graph_revision.txt` 更新标记，供同目录运行的 API 在下次图谱查询时重新核对实体索引；完整缓存指纹含名称、类型、来源和编码器配置。直接在 Neo4j 控制台修改数据时不会产生应用标记，需要重启 API 或显式刷新索引。多主机部署须改用共享的版本通知或数据库版本号，不能依赖单机文件。
