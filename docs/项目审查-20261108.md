## 二、必须修（影响论文结论或正确性）

### 2.1 数值核验基本失效 —— 论文"三道防线"的第三道形同虚设

**位置**：`app/services/citation.py:352-369`

```python
hit = any(
    re.sub(r"\s+", "", c) in haystack_norm for c in candidates if c
)
```

用**子串包含**判断数值是否有据，没有词边界。

**实测复现**（调用真实函数，非推测）：

```
答案「吻合口漏发生率为 7.1%」 vs 证据「文献报告吻合口漏发生率 17.1%」
  → 判为有据：1 条，无据：0 条        ← 应为无据（7.1 是 17.1 的子串）

答案「发生率约 3%」 vs 证据「该研究纳入 2023 例患者」
  → 判为有据：1 条，无据：0 条        ← 应为无据（3 是 2023 的子串）
```

`tests/test_citation.py` 中**没有任何** `verify_numeric_claims` / `extract_numeric_claims` 的测试。

**后果**：`unsupported_numbers`、`numeric_warning` 几乎永远不会触发；论文/答辩若宣称"数值主张核验可拦截无据数字"，**评委只要拿一个 7.1% 对 17.1% 的例子就能驳倒**。

**修法**：改成词边界匹配，并按单位区分

```python
# 数值前后不能紧邻数字或小数点
pattern = rf"(?<![\d.]){re.escape(c)}(?![\d])"
hit = any(re.search(pattern, haystack_norm) for c in candidates if c)
```

再补 3–5 个回归测试（含上述两个反例）。

### 2.2 图谱默认开启且权重 0.6，但实测是负贡献、覆盖率仅 0.6%

**现状**：
- `config.py`：`graph_weight = 0.6`（是 `keyword_weight=0.3` 的两倍）
- 默认 `recall_mode="hybrid"`，即图谱路**默认参与**融合
- 图谱覆盖：**23 / 3,772 个文本块（0.6%）**；1,556 个实体里只有 197 个（12.7%）还有有效来源块

**你自己的复核报告已量化**（`docs/检索评测与复核报告.md`，12 题冻结集）：

| 配置 | Recall@5 | MRR@10 |
|---|---:|---:|
| 仅向量 | 0.750 | 0.456 |
| 向量＋关键词 | 0.833 | **0.542** |
| 向量＋关键词＋**图谱** | 0.833 | **0.340** ← 掉 0.202 |
| 向量＋关键词＋重排 | **0.917** | **0.742** |

即：**加图谱把 MRR 从 0.542 拉到 0.340**，而报告结论也写着"图谱不带重排时降低排序质量，不能宣称图谱在当前题集带来提升"。

**矛盾点**：结论说图谱无益，配置却给它 0.6 的权重并默认开启。答辩演示时若评委问"图谱贡献多少"，答"负贡献"会很难看。

**三个可选方向（实测代价）**

抽取速率取自 11-05 实际构建记录：24 块 / 221.8 秒 = **9.2 秒/块**。
语料构成：指南/共识 30 篇 = **1,497 块**；综述 79 篇 = **2,275 块**。

| 方案 | 具体动作 | 机器耗时 | 覆盖率变化 | 代价与风险 |
|---|---|---|---|---|
| **A 降权/默认关** | `graph_weight 0.6→0.2`（或 0）；`use_graph` 默认 False；前端下拉保留可选 | 2 小时（含重跑 12 题） | 不变（0.6%），但不再拖累默认排序 | 论文需诚实写"图谱为可选路径，当前无增益"；答辩可能被问"图谱白做了" |
| **B 全量扩图** | 3,772 块全部重新 LLM 抽取实体关系，chunk_ids 对齐当前语料 | **约 9.7 小时** + API 费用（文档估 ¥10–50） | 0.6% → 100% | 仍需人工抽查质量；若扩完仍无增益，处境更被动 |
| **C 先扩指南（折中，推荐先做）** | 只对指南/共识的 1,497 块抽取 | **约 3.8 小时** | 0.6% → 约 40% | 若是增益则再决定是否扩全量；若无增益，则"覆盖 40% 仍无提升"是更强的负结论 |

> 为什么先扩指南：指南证据等级最高、实体关系密度最大，最可能产生可测增益。
> 各方案都要重跑同一套 12 题冻结集，才能与现有 0.542 / 0.742 比较。

## 二-补、前端必修（静态审查 + 实测复现）

### F1 流式请求不带 Authorization —— 登录用户的多轮流式会话必然丢失（**已实测复现**）

**位置**：`frontend/src/api/client.ts:626-634`（`ssePost` 的 fetch 头里没有 `Authorization`）

**实测**（我用真实接口跑过）：

```
POST /api/chat/stream（模拟前端 ssePost，不带令牌）→ 建会话 f7eede5d…
GET  /api/chat/{sid} 带 Bearer 令牌（前端 api.conversation 的做法）→ HTTP 404
GET  /api/chat/{sid} 不带令牌（同一 cookie jar）              → HTTP 200
```

**根因**：后端 `chat.py:53-64` 的 `conversation_owner` 优先按 Authorization 判归属，
SSE 没令牌 → 归属 `guest:<cookie>`；而历史查询走 axios（带令牌）→ 按 `user:<id>` 过滤 → 查不到。
`restoreSession` 的 catch 随后会**删掉本地 session id**，于是"切页/刷新后恢复会话"永远失效。

**影响**：登录用户刷新后多轮历史消失且不再尝试恢复；`clearConversation` 同样 404（`cleared:false`），
服务端会话残留；`/qa/stream` 的问答日志 `username` 全空，管理端操作者信息失真。

**修法**（一行级）：`ssePost` 从 localStorage 读 token 并加 `Authorization: Bearer …`，
与 axios 拦截器共用同一份令牌。

### F2 流结束但没有 done/error 时不回调 → 界面永久「生成中」

**位置**：`client.ts:655-672`

读取循环 `break` 后只处理残留 buffer，**不检查是否收到过终态事件**。
代理或服务端发完 delta 直接关流时：ChatView 的 `await new Promise` 永不 resolve（输入框永久禁用、
「停止生成」一直显示）；QaView 的 `status` 停在 `generating`，连"答案可能不完整"的兜底也不触发。

**修法**：记录是否收到 done/error，循环结束时若未结束且非用户中止，调 `onError('流式连接中断，回答可能不完整')`。

### F3 ChatView 流中途出错但已有内容时被标成 done → **把残缺答案显示成完整答案**

**位置**：`ChatView.vue:196-203`（我上一轮写的代码）

```ts
target.status = target.content ? 'done' : 'error'
```

LLM 故障发生在已输出若干 token 之后 → 状态为 `done`：不显示失败、底栏还显示"引用 N 条"。
反过来 `reason === 'no_evidence'` 的正常业务结果（无内容）被渲染成"生成失败"。`reason` 参数完全没用。

**医学场景下这是三条"把残缺呈现为完整"里最危险的一条**，必须改成 `error`（或新增 `partial`）并保留内容。

其他接口排队到 `pool_timeout` 报错。

**修法**：`rag_service._release_connection()` —— 证据打包完成后主动结束事务，
把连接还给连接池；末尾写日志时再短暂申请一次。

**踩到的坑**：第一版把释放放在"读过温度之后"，结果实测仍是 **1 个**
`idle in transaction` —— 因为 `llm.temperature` 从配置表读取时会**新开一个事务**。
把温度解析提前到释放之前，才真正归零。

**实测**（`scripts/measure_stream_connection.py`，一次 71 秒的流式问答期间采样 6 次）：

| 版本 | idle-in-transaction 采样 | 峰值 |
|---|---|---|
| 修复前 | [1, 1, 1, 1, 1, 1] | 1 |
| 修复后 | [0, 0, 0, 0, 0, 0] | **0** |

### 11.2 文献列表不再全量加载文本块与向量

**问题**：`Document.chunks` 关系写成 `lazy="selectin"`，任何 `select(Document)`
都会顺带加载该文献的全部文本块（含 1024 维向量）。列表接口 `limit=200` 时
加载了数万行向量，而响应体只有表头字段。

**修法**：改为 `lazy="select"`；需要块的场景（详情、引用核对）本来就有显式
`selectinload(Document.chunks)`（`kb_repo.get_document`）。

**实测**（三次取中位数）：

| 接口 | 修复前 | 修复后 | 提升 |
|---|---:|---:|---:|
| `/admin/kb/documents?limit=50` | 1199 ms | **86 ms** | 约 14× |
| `/admin/kb/documents?limit=200` | 2889 ms | **116 ms** | 约 25× |

详情接口仍正常返回块（实测 95 条），确认未破坏依赖块的调用。

### 回归

后端 **155 项测试通过**；语料仍为 120 篇 / 4,348 块。

## 十二、剩余 5 项低危问题（2026-11-14）

### 12.1 UUID 路径参数：500 → 422

**问题**：`doc_id` / `log_id` / `feedback_id` / `user_id` / `batch_id` 声明成 `str`，
原样进 SQL，`WHERE id = 'abc'` 触发 PostgreSQL `invalid input syntax for type uuid`，
接口返回 500「服务器内部错误」——而这是客户端输入问题，应为 422。

**修法**：`deps.py` 新增依赖工厂 `path_uuid(param)`，调用点只多一个
`_uuid: Annotated[str, Depends(path_uuid("doc_id"))] = None`，函数体与仓储层不动。

**实测**（5 个端点）：

```
/admin/kb/documents/abc            → 422 ✓
/admin/kb/documents/abc/revisions  → 422 ✓
/admin/qa/logs/abc                 → 422 ✓
/users/abc                         → 422 ✓
/admin/kb/batches/abc              → 422 ✓
```

### 12.2 公开前缀的尾斜杠与子路径豁免

**问题**：原规则 `path != prot_prefix` 判断"是否创建接口本身"，
`POST /api/cases/`（带斜杠）会被判成非创建接口而放行；
同时 `/api/images`、`/api/cases` 下**任何** POST 都豁免，未来新增写操作子路径会默认公开。

**修法**：先规范化去尾斜杠；改为白名单 `PUBLIC_SUBPATHS`
（只放行 `/api/images/similar`、`/api/cases/search` 这两个只读检索端点），
其余子路径仍需认证。

新增 4 个回归用例（尾斜杠、未来子路径）。

### 12.3 切块字符偏移在 overlap 时算错

**问题**：`flush()` 用 `text.find(content[:20], char_cursor)` 反推位置。
带 overlap 时 content 以"上一块尾部"开头，该子串在 `char_cursor` 之前，
`find` 返回 -1 → 偏移退化为 `char_cursor`，整体错位。

**修法**：新增 `sentence_spans()`，切句时记录每句的绝对起止；
聚合时用「首句起点 + 末句终点」，并扣掉首尾空白。

新增 `tests/test_chunker_offsets.py`（3 项）：断言
`text[char_start:char_end].strip() == content.strip()`、起点单调递增、
无 overlap 时同样成立。

### 12.4 影像上传/删除与事务不原子

**问题**：
- 上传：先落盘再 `commit`，提交失败会留下没有数据库记录的孤儿文件
- 删除：先删文件再 `commit`，提交失败则记录还在、文件已丢，`/raw` 变 404

**修法**：
- 上传：commit 失败时回滚并**删除刚写入的文件**（重复上传复用旧记录时不删）
- 删除：拆成「先提交删除行 → 成功后再删文件」，失败最多留可回收孤儿文件

`image_repo.delete()` 改为只删记录，新增 `remove_stored_file(path)`。

### 12.5 ChatView 切页丢当前轮

**问题**：ChatView 未纳入 keep-alive，路由切走立即 `onBeforeUnmount` → abort 流并清空
`turns`；服务端只在 done 时写入会话，这一轮问题与已生成内容永久丢失。

**修法**：`App.vue` 的 `keep-alive :include` 加入 `ChatView`，
切页不卸载、不中止流，回来仍能看到生成结果。

### 回归

后端 **162 项测试通过**（新增 3 项切块偏移、4 个公开路径用例、5 个 UUID 端点实测）；
前端 `tsc` 与 `vite build` 均 0。
