## 二、显卡：8GB 显存怎么用（核心决策）

### 2.0 本机实测结论（已跑通，非估算）

| 检查项 | 实测结果 | 判定 |
|--------|----------|------|
| PyTorch 版本 | **2.11.0+cu128** | ✅ 支持 Blackwell |
| CUDA 构建版本 | 12.8 | ✅ 匹配驱动 573.24 |
| CUDA 可用性 | True | ✅ |
| 计算能力 | **sm_120**（Blackwell） | ✅ 被正确识别 |
| GPU 内核执行 | FP32/FP16 矩阵乘均通过，无 `no kernel image` 错误 | ✅ **决定性验证通过** |
| 有效算力 | FP32 **10.8** / FP16 **34.0** TFLOPS（预热10次/计时50次） | ✅ 符合 8GB 移动版预期 |
| 实测显存 | 总 7.96GB，**基线占用 1.22GB，可用 6.74GB** | ✅ 比预期宽裕 |
| SM 数量 | 26 | — |

**BGE-M3 真实吞吐实测（fp16，本机 GPU，脚本一键复现）**：

| batch_size | 256 条耗时 | 吞吐 |
|------------|-----------|------|
| 8 | 1.67 s | 153 条/秒 |
| 16 | 0.80 s | 322 条/秒 |
| 32 | 0.43 s | 596 条/秒 |
| **64** | **0.37 s** | **694 条/秒** |

模型加载仅 5.7 秒；**BGE-M3 与 reranker 两个模型同时驻留 + 运行时的真实显存占用（nvidia-smi 实测）**：

| 状态 | 显存占用 |
|------|----------|
| 基线（桌面/投屏等常驻） | 2.56 GB |
| 加载 BGE-M3 并跑 512 条（batch 64） | 3.81 GB |
| 再加载 reranker 并精排 64 对 | **4.94 GB（本次峰值）** |
| 其中 PyTorch 实际分配 | 2.13 GB |

**结论：检索侧双模型全开的峰值约 4.94GB，8GB 卡还剩约 3GB 余量，完全可用。**

**检索侧组件实测性能汇总**：

| 组件 | 吞吐 | 说明 |
|------|------|------|
| BGE-M3 向量化 | **694 条/秒**（batch 64） | 20 万文本块全量入库约 **4.8 分钟** |
| bge-reranker-v2-m3 精排 | **105 对/秒** | 一次召回 50 条候选的精排约 0.5 秒 |

> 对照：纯 CPU 跑 20 万块的 embedding 需 1～3 小时。**本机 GPU 把入库环节加速了约 20～35 倍**，这是这块显卡对课题最实在的贡献。建议 embedding `batch_size` 取 32～64；reranker 一次精排 20～50 条候选，延迟约 0.2～0.5 秒，满足交互需求。

> 基线占用在不同时刻波动较大：截图时刻为 2.49GB，实测基线 1.22～2.56GB。差值是 GameViewer 投屏会话与桌面合成器。**按 3GB 基线 + 4.94GB 峰值规划，8GB 有约 3GB 余量，安全。**

### 2.1 两个必须知道的事实

**事实一：RTX 5060 是 Blackwell 架构，计算能力 12.0，必须用 CUDA 12.8+ 的 PyTorch。**

这是最容易踩的坑。RTX 50 系（Blackwell）不再支持 sm_50～sm_70 等老架构，旧的 PyTorch（≤2.4，cu118/cu121 构建）在这张卡上会直接报
`RuntimeError: CUDA error: no kernel image is available for execution on the device`。
必须用 `--index-url https://download.pytorch.org/whl/cu128` 安装 PyTorch 2.7+。同理，vLLM、llama.cpp、bitsandbytes 都要装较新版本，否则同样是内核不兼容。

**事实二：日常已占用 1.25～2.5GB 显存，可用约 5.6～6.7GB。**

截图里 GPU 显示 `0% (53°C)` 却已占用 2.49GB——其中包含一个 `GameViewer Virtual Display Adapter`（远程投屏虚拟显示器），Windows 桌面合成器也会常驻占用。这意味着**你实际能支配的显存不是 8GB，而是约 5.6～6.7GB**。批量处理前建议退出 GameViewer 等投屏/直播类软件、并把浏览器标签页收一收，能多挤出 1～2GB。

### 2.2 显存预算表（含实测值）

| 方案 | 组件 | 预估 | 实测 | 是否可行 |
|------|------|------|------|----------|
| **① 检索本地 + 生成走 API（推荐）** | BGE-M3 + reranker 同时驻留并全速运行 | ≈ 4.4GB | **4.94GB（峰值）** | ✅ 8GB 剩约 3GB，稳 |
| ② 只放 BGE-M3 | BGE-M3 跑 batch 64 | ≈ 2.2GB | **3.81GB** | ✅ 余量充足 |
| ③ 硬塞本地 8B 大模型 | 8B 4bit 权重 5.5～6GB + KV cache 0.5～1GB | ≈ 6.5GB+ | 未测（会超） | ❌ 加上 3GB 基线必然 OOM |
| ④ 8B 模型独占 | 8B 4bit + KV cache，检索模型挪回 CPU | ≈ 6～7GB | 未测 | ⚠️ 勉强，但 CPU 跑 embedding 很慢 |

**推荐采用方案 ①**：本地 GPU 只跑检索侧模型（embedding + 重排），生成和多模态解读走云端 API。理由：

- 你的 CPU 是 16 核 32 线程，但**实测证明 BGE-M3 放 GPU 上收益巨大**：694 条/秒，20 万文本块只需约 4.8 分钟；放 CPU 则要 1～3 小时。这是收益最大的一步。
- 8B 量化模型在医学问答上的幻觉率明显高于云端大模型，答辩演示用它反而有风险。
- 方案 ① 下**全部组件串行执行**：入库时跑 embedding，提问时跑 reranker，二者峰值不叠加；加上云端生成不占显存，8GB 完全够（实测双模型全开峰值 4.94GB，余量约 3GB）。

### 2.3 显存使用纪律（避免半夜 OOM）

```python
# 1) 模型加载后固定显存分配策略
import torch
torch.cuda.set_per_process_memory_fraction(0.85)   # 留 15% 给系统，防碎片化 OOM

# 2) embedding 分块执行，不要一次喂完
#    BGE-M3 单条 512 token：显存 ≈ 2.2GB + batch×0.15GB
#    8GB 卡建议 batch_size ≤ 16；长文本降到 8
model.encode(texts, batch_size=16, max_length=512)

# 3) 两个模型不要长期同时驻留，用完即释放
del model; gc.collect(); torch.cuda.empty_cache()
```

**注意 CUDA 显存碎片化**：反复 load/unload 模型会导致 `torch.cuda.empty_cache()` 也回收不了碎片，最终报 OOM 但 `nvidia-smi` 显示显存没满。解决办法是入库任务和问答服务分成两个独立进程，不要在一个进程里反复切换模型。

### 2.4 省电与温度

这是 8945HX + 5060 的游戏本配置，**必须插电源跑批量任务**：电池模式下 NVIDIA 会限制 GPU 功耗与显存可用量，embedding 速度可能掉一半以上。另外确认 BIOS/厂商软件里把显卡模式设为"独显直连"或至少"混合模式"，纯核显模式会看不到 CUDA 设备。

## 三、硬盘：必须先处理的问题

### 3.1 现状与风险

| 盘符 | 总容量 | 剩余 | 剩余率 | 判断 |
|------|--------|------|--------|------|
| C: | 400GB | **68.8GB** | 17.2% | ⚠️ 偏紧，且 Docker/WSL 默认全在 C: |
| D: | 551.6GB | **138.3GB** | 25.1% | ⚠️ 够装现有计划，但没有余量 |

**风险点**：Docker Desktop 默认把镜像、容器和 WSL2 虚拟磁盘放在**C 盘**（`C:\Users\97657\AppData\Local\Docker` 已占 8GB，实际镜像数据在 WSL 的 ext4.vhdx 里，还会继续膨胀）。本课题需要的容器镜像合计 15～25GB，加上模型权重 5～20GB、文献 100GB+，**C 盘会在你不知不觉中见底**，而 C 盘一满 Windows 会连带出各种诡异故障。所以第一步就是迁移 Docker 存储位置。

### 3.2 建议执行的清理与迁移（按优先级）

```powershell
# ① 把 Docker 数据全部挪到 D 盘（设置 → Resources → Disk image location → 改到 D:\Docker）
#    或在 Docker Desktop 的 settings.json 里改 dataFolder。迁移后 C 盘立刻回收 8GB+。
# ② 把 WSL2 的虚拟磁盘也放到 D 盘（新建发行版时用 --import 指定 D 盘路径）
# ③ 开启 Windows 存储感知，自动清理临时文件与旧更新
# ④ 模型权重、Python venv、语料库一律放 D 盘，不要放 C:\Users 下
# ⑤ 文献按需入库：先入 2000 篇跑通全链路，再按需扩充，不要一次性堆 100GB PDF
```

**空间目标**：让 C 盘保持 ≥40GB 空闲，D 盘保持 ≥80GB 空闲。本方案的落盘分配建议：

| 内容 | 存放位置 | 预估占用 |
|------|----------|----------|
| Python 虚拟环境（含 torch cu128） | `D:\deep seek test\rag-venv` | 8～10GB |
| 模型权重（BGE-M3 + reranker） | `D:\models\` | 约 4.5GB |
| Docker 镜像与数据 | `D:\Docker\` | 15～25GB |
| 原始文献 PDF/Word | `D:\kb\raw\` | 50～150GB（按需增长） |
| PostgreSQL / Neo4j 数据卷 | `D:\deep seek test\data\` | 5～10GB |

> **注意 PyTorch cu128 的下载量**：torch + torchvision + 配套 CUDA 运行库合计约 3～5GB 下载、8～10GB 落盘，务必确认装在 D 盘。本机 `nvidia-smi` 显示的 CUDA 12.8 是**驱动支持的最高版本**，PyTorch 自带运行库，不需要单独安装 CUDA Toolkit。

## 五、国内网络下载模型：实测踩坑与解法

本机在国内网络环境下拉取 HuggingFace 模型会遇到两个具体问题，**都已实测复现并解决**，记录下来可直接复用。

### 5.1 必须设置镜像端点

直连 huggingface.co 会超时，改用镜像（实测 2～13 MB/s）：

```powershell
$env:HF_ENDPOINT="https://hf-mirror.com"
$env:HF_HOME="D:\models\hf"        # 模型一律放 D 盘，别让它落到 C 盘
```

### 5.2 FlagEmbedding 默认下载必然失败（已实测定位根因）

**现象**：`BGEM3FlagModel('BAAI/bge-m3')` 报 `403 Forbidden`，URL 里带着 `imgs/.DS_Store`。即使本地缓存已完整，重跑依然报同样的错。

**根因**（读 FlagEmbedding 源码确认）：`FlagEmbedding/finetune/embedder/encoder_only/m3/runner.py` 第 64～69 行是

```python
if not os.path.exists(model_name_or_path):
    model_name_or_path = snapshot_download(
        repo_id=model_name_or_path,
        cache_dir=cache_folder,
        ignore_patterns=['flax_model.msgpack', 'rust_model.ot', 'tf_model.h5']   # 注意：没有过滤图片
    )
```

它**只要收到的是仓库名（而非本地路径）就会拉取仓库全部文件**，其 `ignore_patterns` 只排除了 flax/rust/tf 三种权重，**没有排除 `imgs/`**。而 BGE-M3 仓库里混有 macOS 垃圾文件 `imgs/.DS_Store`，镜像站对其返回 403，于是整个加载失败。**不是模型问题、不是网络问题、也不是权限问题。**

**解法**：先用 `allow_patterns` 把模型下到**本地真实目录**，之后一律用本地路径加载——`os.path.exists()` 为真，直接跳过下载与网络请求。

```powershell
$env:HF_ENDPOINT="https://hf-mirror.com"
$env:HF_HOME="D:\models\hf"
& "D:\deep seek test\rag-venv\Scripts\python.exe" "D:\deep seek test\download_models.py"
```

脚本已放在工作区：[download_models.py](download_models.py)，同时下载 `bge-m3` 与 `bge-reranker-v2-m3` 到 `D:\models\`，并做完整性校验。

加载时改用**本地路径**（关键）：

```python
from FlagEmbedding import BGEM3FlagModel
model = BGEM3FlagModel(r"D:\models\bge-m3", use_fp16=True, device="cuda")   # 不是 'BAAI/bge-m3'
```

> **两个易错点**：
> 1. BGE-M3 仓库里**没有** `model.safetensors`，只有 `pytorch_model.bin`（实测 2165.9 MB）。网上很多教程写 `safetensors`，在本仓库会 404。
> 2. 只做 `hf_hub_download` 逐个下文件是**不够的**——因为 FlagEmbedding 仍会走 `snapshot_download`，必须落到本地目录并用本地路径加载才彻底解决。

### 5.3 reranker 下载报 401 Unauthorized（xet 存储后端问题）

**现象**：用 `snapshot_download` 拉 `BAAI/bge-reranker-v2-m3` 时报

```
CAS Client Error: ... (401 Unauthorized),
domain: https://cas-server.xethub.hf.co/v2/reconstructions/...
```

**根因**：新版 huggingface_hub 默认启用 **xet 存储后端**（HuggingFace 的新传输协议），镜像站不支持该后端，于是鉴权失败。这跟你的账号权限无关。

**解法**：禁用 xet 后端后逐个文件下载——已验证有效。

```powershell
$env:HF_HUB_DISABLE_XET="1"
```

脚本 [download_models.py](download_models.py) 中已可复用同样思路（如遇 401 请设该环境变量后重跑）。

> **注意两个仓库的主权重格式不同**，别照抄：
> - `BAAI/bge-m3` → `pytorch_model.bin`（2165.9 MB）
> - `BAAI/bge-reranker-v2-m3` → `model.safetensors`（2165.9 MB）

### 5.4 Windows 符号链接警告（可忽略）

会看到 `your machine does not support them in D:\models\hf\...` 的警告。含义是 HuggingFace 缓存无法用符号链接去重，会**多占一点磁盘**，功能不受影响。想消除警告可开启 Windows「开发者模式」，或设 `$env:HF_HUB_DISABLE_SYMLINKS_WARNING="1"`。

### 5.5 下载时留意磁盘

pip 下载 torch 的 2.7GB wheel 时会先在 **C 盘临时目录**解包，并在 `C:\Users\97657\AppData\Local\pip\cache` 留下 **3.42GB** 缓存（本次实测）。装完可清理：

```powershell
& "D:\deep seek test\rag-venv\Scripts\python.exe" -m pip cache purge
```

## 七、本地模型能力边界（别踩的坑）

| 想做的事 | 本机能否做 | 说明 |
|----------|------------|------|
| 文献 embedding（BGE-M3） | ✅ 很合适 | GPU 上 20 万块约几分钟 |
| 检索结果重排（bge-reranker-v2-m3） | ✅ 很合适 | 单次几十毫秒 |
| 本地跑 8B 对话模型 | ⚠️ 勉强不建议 | 需独占显存，且与检索模型抢卡；用 API 更省心 |
| 本地跑 Qwen2.5-VL 做影像解读 | ❌ 不行 | 7B 视觉模型 fp16 需约 16GB 显存，远超 8GB |
| 本地微调 BERT 做实体识别 | ✅ 可行 | 用 LoRA + batch 8 左右，8GB 能训 base 级模型 |
| 本地微调 7B 大模型 | ❌ 不现实 | 显存不足，建议租云 GPU（约 ¥2～10/小时） |

**离线演示预案**：如果答辩现场没网、又要展示"本地推理"，不要临时赌 8B 模型能否装下。更稳的做法是提前把 20～30 道演示问答的结果缓存进 Redis，并在界面上明确标注"演示模式：使用缓存结果"。这比现场 OOM 崩溃体面得多。

**这台机器完全能完成本课题，且 CPU/内存富余，无需再买硬件。**

已在你的机器上完成的实测（可直接作为开题/中期报告的环境验证材料）：

| 环节 | 结果 |
|------|------|
| PyTorch cu128 + RTX 5060 (sm_120) | ✅ 已装好并验证内核可执行 |
| 有效算力 | FP32 10.8 / FP16 34.0 TFLOPS |
| BGE-M3 向量化 | ✅ **694 条/秒**，20 万块约 4.8 分钟 |

2. **把 Docker 数据和模型权重从 C 盘迁到 D 盘**——C 盘只剩 69GB，是本机最大的实际风险；
